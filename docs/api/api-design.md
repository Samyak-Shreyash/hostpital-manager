# HMS Release 1 — REST API Design (v0.2, draft)

Base path `/api/v1`. Full OpenAPI is generated from code (springdoc); this document fixes contracts, rules and authorization before implementation.

## 1. Conventions
| Topic | Rule |
|---|---|
| Auth | Session cookie `HMSSESSION` (HttpOnly, Secure, SameSite=Lax). State-changing requests need header `X-XSRF-TOKEN` (value from `XSRF-TOKEN` cookie) |
| Org scoping | Derived from session principal. Never accepted in body/query. Cross-org ids → `404` |
| Content | `application/json; charset=utf-8`. camelCase. Instants ISO-8601 UTC (`2026-11-06T09:30:00Z`). Dates `YYYY-MM-DD`. Money = decimal **string** `"1250.00"` |
| IDs | Opaque strings (UUIDv7 server-side, ADR-0004); clients must not parse or validate their format. Patient-facing material uses business keys (UHID, invoice no.) |
| Pagination | `?page=0&size=20` (max 100), `sort=field,dir`. Response envelope `{ "items": [], "page": 0, "size": 20, "totalItems": 134 }` |
| Concurrency | Mutable resources return `version`; updates send `version`; mismatch → `409 CONCURRENT_MODIFICATION` |
| Idempotency | `Idempotency-Key: <uuid>` required on `POST /payments`, `/refunds`, `/invoices/{id}/issue`; same key+payload returns original response |
| Correlation | Request `X-Request-Id` accepted (1–64 chars of `A-Za-z0-9._-`; anything else is replaced) or generated; echoed in the response header, as `requestId` in every error, and as `correlationId` in logs |
| Errors | RFC 7807 (below) |
| Methods | POST create/commands; PATCH partial update; no DELETE for clinical/financial data (use status commands) |

### Error model
```json
{
  "type": "https://hms.example/problems/validation-error",
  "title": "Validation failed",
  "status": 422,
  "code": "VALIDATION_ERROR",
  "detail": "One or more fields are invalid.",
  "requestId": "6f1c9d0e-3a7b-4a39-9d5b-0c7b1b5a9e11",
  "errors": [ { "field": "dateOfBirth", "code": "NOT_IN_FUTURE", "message": "Date of birth cannot be in the future." } ]
}
```
| HTTP | code examples |
|---|---|
| 400 | MALFORMED_REQUEST |
| 401 | UNAUTHENTICATED, INVALID_CREDENTIALS, SESSION_EXPIRED |
| 403 | FORBIDDEN (missing permission), ACCOUNT_INACTIVE, PASSWORD_CHANGE_REQUIRED |
| 404 | NOT_FOUND (also for cross-org) |
| 409 | CONCURRENT_MODIFICATION, SLOT_CONFLICT, BED_NOT_AVAILABLE, PATIENT_ALREADY_ADMITTED, INVOICE_IMMUTABLE, IMMUTABLE_RECORD, EXCEEDS_OUTSTANDING, ENCOUNTER_FINALIZED, INVALID_STATE_TRANSITION, DUPLICATE_SUSPECTED |
| 422 | VALIDATION_ERROR, BUSINESS_RULE_VIOLATION |
| 423 | ACCOUNT_LOCKED |
| 429 | RATE_LIMITED |
| 500 | INTERNAL_ERROR (no internals leaked) |

Framework errors without a domain code use the status name (e.g. `405 METHOD_NOT_ALLOWED`, `415 UNSUPPORTED_MEDIA_TYPE`). `type` is `https://hms.example/problems/<code in kebab-case>`. Field errors never echo the rejected value. Implemented by `com.hms.shared.web.ProblemDetailsHandler`; shared exceptions: `NotFoundException` (404), `ConflictException(code)` (409), `BusinessRuleException([code])` (422).

Permission codes are listed per endpoint. `*` = see role mapping in PRD.

## 2. Authentication
| Method & path | Purpose | Permission |
|---|---|---|
| POST `/auth/login` | Create session | public (rate limited) |
| POST `/auth/logout` | End session | authenticated |
| GET `/auth/me` | Current user, org, permission list | authenticated |
| POST `/auth/change-password` | Change own password | authenticated |
| POST `/auth/mfa/verify` | Second factor (when enabled) | pre-auth session |

```http
POST /api/v1/auth/login
{ "email": "reception1@demo-clinic.example", "password": "••••••••" }
```
```json
200 { "user": { "id": "0192…", "fullName": "Demo Receptionist", "roles": ["RECEPTIONIST"], "mustChangePassword": false },
      "permissions": ["patient:read","patient:create","appointment:create"],
      "organization": { "id": "0192…", "name": "Demo Clinic", "timezone": "Asia/Kolkata" } }
```
Validation: email format; password 1–128 chars (policy applies on set, not login; a password over 72 UTF-8 bytes can never be correct and is an ordinary `401 INVALID_CREDENTIALS` that counts towards the lockout). Failure always `401 INVALID_CREDENTIALS` (identical body for unknown user / wrong password; unknown emails still run one BCrypt check so timing matches); lock after 5 failures for 15 min → `423 ACCOUNT_LOCKED`, also for the right password while locked; right password on an inactive account → `403 ACCOUNT_INACTIVE`. Login needs the CSRF header too: the SPA gets the `XSRF-TOKEN` cookie from any earlier response (e.g. `GET /auth/me`, even when it answers 401). The session id is rotated on every login. Rate limit (reverse proxy, `infra/proxy/nginx.conf`): per client IP, burst of 20 then 30/min; excess gets `429 RATE_LIMITED` Problem+JSON with `Retry-After: 5`. Sized for a clinic behind one NAT address; behind another load balancer the proxy must use the real client IP. `roles` (role codes) and `permissions` are loaded from the database at login and fixed for the session; a role change applies from the next login (ADR-0006). `organization` carries `id`, `name` and `timezone` (`[E2-1]`). Endpoints check permissions only (`hasAuthority('patient:read')`); an architecture test rejects any `@PreAuthorize` using `hasRole`/`hasAnyRole`. The catalogue is `com.hms.identity.api.Permissions` (database-design.md section 13).

`POST /auth/change-password` `{ "currentPassword", "newPassword" }` -> `204` (authenticated, CSRF header required). Policy (`com.hms.identity.domain.PasswordPolicy`, reused for admin-set temporary passwords): 12 characters to 72 UTF-8 bytes (BCrypt limit), not blank, not equal to the account email, no composition rules, no history; the new password must also differ from the current one. Violations are `422 PASSWORD_POLICY_VIOLATION` (rule names only); a wrong current password is `422 INVALID_CURRENT_PASSWORD` and counts towards the login lockout (a locked account gets `423 ACCOUNT_LOCKED`). Audited as `PASSWORD_CHANGED` (fields `passwordHash`, `mustChangePassword`) or `PASSWORD_CHANGE_FAILED`; passwords are never logged or audited. A successful change clears `must_change_password` and the lockout counters. While `must_change_password` is set, every `/api/**` call except `/auth/me`, `/auth/logout` and `/auth/change-password` returns `403 PASSWORD_CHANGE_REQUIRED` (checked against the database on each request, so it clears immediately); `/auth/me` reports the real `mustChangePassword`.

## 3. Users & roles
| Method & path | Purpose | Permission |
|---|---|---|
| GET `/users` ?status,role,q | List | `user:read` |
| POST `/users` | Create | `user:create` |
| GET `/users/{id}` | Detail | `user:read` |
| PATCH `/users/{id}` | Update name/roles | `user:update` |
| POST `/users/{id}/activate` · `/deactivate` | Lifecycle (deactivate kills sessions) | `user:update` |
| POST `/users/{id}/reset-password` | Admin reset → temp password, must change | `user:reset-password` |
| GET `/roles` · GET `/permissions` | Reference | `role:read` |
| POST `/roles` · PATCH `/roles/{id}` | Manage custom roles / permissions | `role:manage` |

```json
POST /users
{ "email": "dr.rao@demo-clinic.example", "fullName": "Dr. A. Rao", "roleCodes": ["DOCTOR"] }
→ 201 { "id": "…", "status": "ACTIVE", "mustChangePassword": true, "temporaryPassword": "shown-once", "version": 0 }
```
Rules: email unique across **all** organizations, case-insensitive (`409 DUPLICATE_EMAIL`), because login is email-only (owner decision 2026-11-12; an org selector would be needed before relaxing this for multi-tenant SaaS); cannot deactivate self (`409 CANNOT_DEACTIVATE_SELF`); cannot remove last active system administrator (`409 LAST_ADMINISTRATOR`). Temporary password is returned once (create and reset-password responses, `Cache-Control: no-store`) and never logged/audited; it is 16 characters, meets the password policy, and sets `mustChangePassword`.

Implementation notes (`[E1-7]`, `UserController`, `RoleController`):
- List `GET /users ?status=ACTIVE|INACTIVE &role=<roleCode> &q=<substring of name or email> &ids=<uuid>&ids=... &sort=name|email|status|createdAt (prefix "-" for descending; default name) &page &size` uses the section 1 envelope; `ids` (at most 100) returns only those users of the caller's organization (unknown and other-org ids are simply not matched), used by the audit viewer to show actor names; an unknown `sort` is `422 VALIDATION_ERROR`; detail and list rows carry `id, email, fullName, status, mustChangePassword, roleCodes, version, createdAt, updatedAt`. Detail is audited (`USER_VIEWED`), the list is not.
- `PATCH /users/{id}` `{ "version", "fullName"?, "roleCodes"? }`: `version` is required (`409 CONCURRENT_MODIFICATION` on mismatch); `roleCodes`, when present, replaces the whole set; unknown codes (including another organization's) are `422 UNKNOWN_ROLE`; at least one of the two fields is required.
- **Bulk import** (UI issue U4) `POST /users/import` (`user:create`) `{ "users": [ { email, fullName, roleCodes }, ... ] }` (1-200 rows, each validated like `POST /users`) -> `201 { "items": [ <user with temporaryPassword> ] }`, `Cache-Control: no-store`. All or nothing: every row is checked first, and if any fails nothing is created and the answer is `422 IMPORT_REJECTED` with `rows: [{ row (1-based), code, message }]` (codes `DUPLICATE_IN_FILE`, `DUPLICATE_EMAIL`, `UNKNOWN_ROLE`, `PRIVILEGE_ESCALATION`); a malformed row is `422 VALIDATION_ERROR` with field paths `users[<0-based>].<field>`. Each created user is audited as `USER_CREATED`. The client parses the CSV (`email,fullName,roles`, roles separated by `;`); the server never receives the file.
- `activate` / `deactivate` are idempotent (no change, no audit when already in that state). Deactivation deletes all of the user's `spring_session` rows.
- `reset-password` returns the full user plus `temporaryPassword`, clears the lockout and ends the user's other sessions. A role change ends the user's sessions too (so it applies immediately instead of at next login); a user changing their own account keeps the current session. `POST /auth/change-password` also ends the user's other sessions and keeps the current one.
- "System administrator" is defined by permission, not role name: an active user whose roles together grant both `user:update` and `role:manage`. Any change (deactivation, role replacement, editing a role's permissions) that would take the count from at least one to zero is `409 LAST_ADMINISTRATOR`; such changes serialize on a lock of the organization row.
- No privilege escalation: a caller may grant a role only permissions the caller holds (`POST /roles`, and permissions *added* by `PATCH /roles/{id}`), and may assign to a user only roles whose every permission the caller holds (`POST /users`, and roles *added* by `PATCH /users/{id}`). Otherwise `403 PRIVILEGE_ESCALATION`, nothing changes. Permissions/roles a target already has are not re-checked. There is no exemption for any caller, system administrators included; only the first-run bootstrap (system, no caller) is outside the rule. Exception, `role:assign` (owner decision 2026-11-13): a caller holding `role:assign` (in addition to `user:create` / `user:update`) may assign a **built-in default role** (a role whose code is one of the default templates: SYSTEM_ADMIN, FACILITY_ADMIN, DOCTOR, NURSE, RECEPTIONIST, ACCOUNTANT) without holding its permissions, so the default SYSTEM_ADMIN (which holds `role:*` and no clinical permissions) can staff the organization. It applies only while that role's current permission set is still within its default template; a built-in role an administrator has edited beyond its template (any extra permission) falls back to the strict rule above, so editing a role never makes it a back door. Narrowing a built-in role keeps it covered. Custom roles always follow the strict rule, and `role:assign` never allows granting permissions: `POST /roles` and `PATCH /roles/{id}` stay subset-only. The default SYSTEM_ADMIN template holds `role:assign` (via `role:*`; no other template uses that wildcard); migration V12 adds the permission and backfills existing organizations.
- Logging in (success, failed attempt, lockout) does not change a user's `version`, so it never causes `409 CONCURRENT_MODIFICATION` on an administrator's pending edit.
- Roles: `GET /roles` returns `[{ id, code, name, permissions[], version, createdAt, updatedAt }]` of the caller's organization; `GET /permissions` returns the catalogue as a JSON array of codes. `POST /roles` `{ code ^[A-Z][A-Z0-9_]{0,49}$, name, permissionCodes[] }` -> `201` (`409 DUPLICATE_ROLE_CODE`, `422 UNKNOWN_PERMISSION`); `PATCH /roles/{id}` `{ version, name?, permissionCodes? }` replaces the permission set and ends the sessions of every holder. Roles are never deleted and have no status.
- Audit actions (entity `APP_USER` / `ROLE`, field names only): `USER_CREATED`, `USER_UPDATED`, `USER_ACTIVATED`, `USER_DEACTIVATED`, `USER_PASSWORD_RESET`, `USER_VIEWED`, `ROLE_CREATED`, `ROLE_UPDATED`.

## 4. Organization, departments, specialties
| Method & path | Permission |
|---|---|
| GET `/organization` · PATCH `/organization` (name, timezone, address, gstin) | `org:read` · `org:update` |
| GET/POST `/departments`, PATCH `/departments/{id}` | `catalog:read` / `catalog:manage` |
| GET/POST `/specialties`, PATCH `/specialties/{id}` | `catalog:read` / `catalog:manage` |
| GET `/services`, GET `/services/{id}`, GET `/services/{id}/prices` | `catalog:read` |
| POST `/services`, PATCH `/services/{id}`, POST `/services/{id}/prices` | `catalog:manage` |
```json
POST /departments { "code": "CARDIO", "name": "Cardiology" } → 201 { "id":"…","code":"CARDIO","name":"Cardiology","active":true,"version":0 }
```
Rules: code `[A-Z0-9_]{2,20}`, unique per org. No delete; `active=false`. Timezone must be valid IANA id.

**Departments and specialties (`[E2-2]`)**: both lists have the same shape `{ id, code, name, active, version, createdAt, updatedAt }`. `GET /departments|/specialties` `?active=true|false&page=0&size=50` (size 1-100, ordered by code) returns the pagination envelope `{ items, page, size, totalItems }` for the caller's organization. `POST` `{ "code", "name" }`: code `[A-Z0-9_]{2,20}` (upper case only), name 1-100 chars; a duplicate code in the same organization is `409 DUPLICATE_DEPARTMENT_CODE` / `DUPLICATE_SPECIALTY_CODE` (another organization may use the same code). `PATCH /{id}` `{ "version", "name"?, "active"? }`: `version` required (`409 CONCURRENT_MODIFICATION` on mismatch), at least one of `name`/`active`, the code is immutable; `active=false` deactivates and `active=true` reactivates; another organization's id is `404`. There is no DELETE (`405`) and no database DELETE grant. Invalid input is `422 VALIDATION_ERROR`. Audit (entity `DEPARTMENT` / `SPECIALTY`, field names only): `*_CREATED`, `*_UPDATED`, `*_DEACTIVATED`, `*_ACTIVATED`. The default Facility Administrator role holds `catalog:*`.

**Service catalog and prices (`[E2-3]`, billing module)**: `GET /services` `?active=&page=0&size=50` (ordered by code, pagination envelope) and `GET /services/{id}` return `{ id, code, name, active, currentPrice, version, createdAt, updatedAt }`; `currentPrice` is the price valid now as a decimal string (`"500.00"`), `null` before the first price. `POST /services` `{ code [A-Z0-9_]{2,30}, name 1-150 }` -> `201` (`409 DUPLICATE_SERVICE_CODE`); `PATCH /services/{id}` `{ version, name?, active? }` as for departments (`409 CONCURRENT_MODIFICATION`); no DELETE. Prices are append-only versions: `GET /services/{id}/prices` (newest first, paged) returns `{ id, serviceId, amount, effectiveFrom, effectiveTo, createdAt }`; `POST /services/{id}/prices` `{ amount, effectiveFrom? }` -> `201`. `amount` is a decimal string with at most 2 decimals and >= 0 (JSON numbers or extra precision are `400`, negative is `422 VALIDATION_ERROR`); `effectiveFrom` defaults to now and may not be in the past (`422 PRICE_EFFECTIVE_IN_PAST`). A version is valid for `effectiveFrom <= t < effectiveTo` (half-open): the new version closes the previous open-ended one at its own start, so exactly one price applies at any instant. A new version must start after the latest version's start, otherwise `409 PRICE_RANGE_OVERLAP` (the database exclusion constraint backs this under concurrency, same code). A price is never edited or deleted; invoices copy the price, so a change never alters an invoice. Other modules read prices through `com.hms.billing.api.ServicePriceLookup#priceAt(organizationId, serviceId, instant)`. Audit: `SERVICE_CREATED|UPDATED|DEACTIVATED|ACTIVATED` (entity `SERVICE`) and `SERVICE_PRICE_CREATED` (entity `SERVICE_PRICE`, fields `serviceId, amount, effectiveFrom`; never values).

**Organization settings (`[E2-1]`)**: no id in the path, the organization is always the caller's (never from input).
`GET /organization` -> `{ id, name, timezone, gstin?, address?, duplicateDobThreshold, duplicatePhoneThreshold, version, createdAt, updatedAt }`. `PATCH /organization` `{ "version", "name"?, "timezone"?, "gstin"?, "address"?, "duplicateDobThreshold"?, "duplicatePhoneThreshold"? }`: `version` required (`409 CONCURRENT_MODIFICATION` on mismatch), at least one other field, omitted fields untouched, an empty `gstin`/`address` clears it. `name` 1-200 chars; `timezone` a region-based IANA id (`Asia/Kolkata`, `UTC`; offsets such as `+05:30` are rejected); `gstin` optional, 15 characters in the GSTIN format `^[0-9]{2}[A-Z]{5}[0-9]{4}[A-Z][1-9A-Z]Z[0-9A-Z]$` (format only, the check digit is not verified); `address` up to 500 chars; the patient duplicate thresholds (`[E3-3]`, BR-P3; defaults `0.45` and `0.30`) are JSON numbers greater than 0 and at most 1 with at most 2 decimals. Invalid input is `422 VALIDATION_ERROR`. Audit: `ORGANIZATION_UPDATED` (entity `ORGANIZATION`, field names only) and `ORGANIZATION_CREATED` (bootstrap).

**First-run bootstrap**: on startup, if no organization exists and `HMS_BOOTSTRAP_ORG_NAME` + `HMS_BOOTSTRAP_ADMIN_EMAIL` are set (`HMS_BOOTSTRAP_ORG_TIMEZONE` optional, default `Asia/Kolkata`), the app creates the organization, the default roles and a System Administrator (`mustChangePassword = true`) with a generated temporary password. The password is written only to the file named by `HMS_BOOTSTRAP_ADMIN_PASSWORD_FILE` (owner-only permissions where the OS supports them) and is never logged or audited; the variables without the file variable fail startup. A second start finds an organization and does nothing.

## 5. Doctors (practitioners)
| Method & path | Permission |
|---|---|
| GET `/doctors` ?specialtyId,departmentId,q | `practitioner:read` |
| POST `/doctors` | `practitioner:create` |
| GET/PATCH `/doctors/{id}` | read/update |
| PUT `/doctors/{id}/specialties` (replace set) | `practitioner:update` |
| PUT `/doctors/{id}/departments` | `practitioner:update` |
| PUT `/doctors/{id}/availability` (weekly template) | `practitioner:schedule` |
| POST `/doctors/{id}/availability-exceptions` | `practitioner:schedule` |
| GET `/doctors/{id}/slots` `?date=` or `?from&to` (free slots) | `appointment:read` |
```json
POST /doctors
{ "userId": "…", "fullName": "Dr. A. Rao", "registrationNo": "TSMC-12345", "registrationCouncil": "TSMC",
  "qualifications": ["MBBS","MD"], "specialtyIds": ["…"], "primarySpecialtyId": "…", "departmentIds": ["…"], "defaultSlotMinutes": 15 }
→ 201 { "id":"…", "status":"ACTIVE", "version":0, … }
PUT /doctors/{id}/availability
{ "windows": [ { "weekday": 1, "start": "09:00", "end": "13:00", "slotMinutes": 15 } ] }
```
Rules: ≥1 specialty; exactly one primary; windows on same weekday may not overlap; end > start; slotMinutes 5–120. Staff: `/staff`, see **Implemented (`[E4-2]`)** below.

**Implemented (`[E4-3]`)**: `GET /doctors/{id}/availability` (`practitioner:read`) and `PUT /doctors/{id}/availability` (`practitioner:schedule`) `{ version, windows: [{ weekday 1=Mon..7=Sun, start "HH:mm", end "HH:mm", slotMinutes? }] }` -> `{ practitionerId, timezone, windows, version }`. Times are local to the organization timezone; `version` is the doctor's (replacing bumps it, `409 CONCURRENT_MODIFICATION` on mismatch); at most 50 windows; `slotMinutes` 5-120 (default `defaultSlotMinutes`), a window must hold at least one slot; overlapping windows on a weekday are `422 AVAILABILITY_OVERLAP` (also a DB exclusion constraint). Leave: `POST /doctors/{id}/availability-exceptions` `{ date, start?, end? }` (both times or neither; neither = whole day) -> `201 { id, practitionerId, date, start, end, wholeDay, status, version, createdAt, updatedAt }`; `GET .../availability-exceptions?from&to` (`practitioner:read`, at most 500); `POST .../availability-exceptions/{exceptionId}/cancel` `{ version }` -> `status: CANCELLED` (leave is never deleted). Free slots: `GET /doctors/{id}/slots?date=` or `?from=&to=` (inclusive, at most 31 days, else `422 VALIDATION_ERROR`; `appointment:read`) -> `{ practitionerId, timezone, from, to, slots: [{ startAt, endAt }] }` (UTC instants). Slots come from the windows in the organization timezone, minus active leave; an inactive doctor has none. Free slots DO subtract booked times (owner decision Q9, 2026-11-18): the appointment module supplies them through the `BookedTimes` port (`[E5-1]`), so a booked slot no longer appears; bookings that clash with leave are flagged, never cancelled. Audit: `PRACTITIONER_AVAILABILITY_CHANGED` (entity `PRACTITIONER`, field `windows`), `AVAILABILITY_EXCEPTION_CREATED` / `AVAILABILITY_EXCEPTION_CANCELLED` (entity `AVAILABILITY_EXCEPTION`). Another organization's doctor id is `404`.
**Implemented (`[E4-1]`)**: `POST /doctors` -> `201` with `{ id, userId, fullName, registrationNo, registrationCouncil?, qualifications, defaultSlotMinutes, status, primarySpecialtyId, specialtyIds, departmentIds, version, createdAt, updatedAt }` (same shape from `GET /doctors/{id}`; `GET /doctors` returns it in the pagination envelope, filters `specialtyId`, `departmentId`, `q` (name or registration number, case-insensitive substring), `status` ACTIVE/INACTIVE). Rules: `userId` must be an active user of the caller's organization, else `422 USER_NOT_AVAILABLE` (unknown and other-org ids answer the same); a user already linked to a doctor or a staff record is `409 USER_ALREADY_LINKED`; `registrationNo` (1-50 of letters, digits, `/`, `.`, `-`; stored upper-cased) is unique per organization, else `409 DUPLICATE_REGISTRATION_NO`; `registrationCouncil` up to 100 chars; `qualifications` up to 10, each 1-50; `defaultSlotMinutes` 5-120 (default 15); `specialtyIds` 1-20 distinct and `primarySpecialtyId` required and one of them (exactly one primary, also enforced in the database: a commit that would leave a doctor with no primary specialty is refused by a deferred trigger, SQLSTATE `HM002`, and answered `422 PRIMARY_SPECIALTY_REQUIRED`); `departmentIds` 0-20 distinct. A specialty or department id that is unknown, of another organization, or inactive is `422 SPECIALTY_NOT_AVAILABLE` / `DEPARTMENT_NOT_AVAILABLE` (an inactive one already assigned may stay). Other invalid input is `422 VALIDATION_ERROR`.
`PATCH /doctors/{id}` `{ version, fullName?, registrationNo?, registrationCouncil? ("" clears), qualifications?, defaultSlotMinutes?, status? }`; `PUT /doctors/{id}/specialties` `{ version, specialtyIds, primarySpecialtyId }`; `PUT /doctors/{id}/departments` `{ version, departmentIds }` (empty list clears). All need `version` (`409 CONCURRENT_MODIFICATION` on mismatch); an unchanged body is a no-op. Doctors are never deleted (`status: INACTIVE`). Another organization's doctor id is `404`. Audit (entity `PRACTITIONER`, field names only): `PRACTITIONER_CREATED`, `PRACTITIONER_UPDATED`, `PRACTITIONER_SPECIALTIES_CHANGED`, `PRACTITIONER_DEPARTMENTS_CHANGED`. Permissions: catalogue entries `practitioner:read|create|update` (V4), held by the default Facility Administrator role.

**Implemented (`[E4-2]`)**: Staff (non-doctor personnel; domain-model `Staff`, own table `staff`, V19) use their own `staff:read|create|update` permissions (owner decision 2026-11-14, V21), independent of the doctor endpoints' `practitioner:*`; a role may hold both. The default Facility Administrator holds both sets; V21 backfills existing organizations. `POST /staff` `{ userId, fullName, staffType, designation?, departmentId? }` -> `201` with `{ id, userId, fullName, staffType, designation, departmentId, status, version, createdAt, updatedAt }` (same shape from `GET /staff/{id}`; `GET /staff` returns it in the pagination envelope, filters `staffType`, `departmentId`, `q` (name substring), `status`). `staffType` is one of `NURSE`, `RECEPTIONIST`, `ACCOUNTANT`, `LAB_TECHNICIAN`, `PHARMACIST`, `ADMINISTRATIVE`, `OTHER`; `designation` up to 80 chars. Every staff record links to exactly one active user of the caller's organization, else `422 USER_NOT_AVAILABLE` (unknown and other-org ids answer the same); a user is at most one doctor **or** one staff record, else `409 USER_ALREADY_LINKED` (also enforced in the database). A department that is unknown, of another organization or inactive is `422 DEPARTMENT_NOT_AVAILABLE` (an inactive one already assigned may stay). `PATCH /staff/{id}` `{ version, fullName?, staffType?, designation? ("" clears), departmentId?, clearDepartment?, status? }`; a stale `version` is `409 CONCURRENT_MODIFICATION`. There is no delete: deactivate with `status: INACTIVE`. Changes are audited (`STAFF_CREATED`, `STAFF_UPDATED`) with field names only. **Roles** are not part of the staff resource: they belong to the linked user and are assigned only through `PATCH /users/{userId}` (`[E1-7]`, `user:update` + `role:assign` rules and privilege-escalation checks); the staff API neither reads nor changes them.

## 6. Patients
| Method & path | Purpose | Permission |
|---|---|---|
| POST `/patients` | Register (dup check) | `patient:create` (+ `patient:override-duplicate` to confirm a suspected duplicate) |
| GET `/patients` ?q,uhid,phone,dob | Search (fuzzy name) | `patient:search` |
| GET `/patients/{id}` | Detail (audited view) | `patient:read` |

**Allergies and medical history (`[E3-4]`, V17).** Append-only: `POST` adds an entry (allergy `{substance, reaction?, severity MILD|MODERATE|SEVERE}`, history `{condition, notes?}`); content is never edited and nothing is deleted. `PATCH` accepts only `{"status":"ENTERED_IN_ERROR"}` (anything else `422 VALIDATION_ERROR`); the entry stays listed with `status: ENTERED_IN_ERROR` and `enteredInErrorAt`. **Implemented by `[E3-5]`: `PATCH /patients/{id}`** (`patient:update`). Body `{ version, fullName?, sex?, dateOfBirth?, dobEstimated?, phone?, address?, emergencyContact?, abhaNumber?, identityChangeReason?, confirmNotDuplicate?, overrideReason? }`; `version` is required (`409 CONCURRENT_MODIFICATION` on mismatch; the row is locked `FOR UPDATE` first, so of two concurrent edits with the same version one wins and the other gets `409`). Omitted fields are unchanged; formats as for registration (bare 10-digit phones get `+91`). Every field except the UHID is editable: a `uhid` in the body is `422 UHID_IMMUTABLE`. `status` is not editable here (lifecycle commands come later). Owner decision 2026-11-13: changing `fullName`, `sex`, `dateOfBirth` or `dobEstimated` also needs `patient:update-identity` (else `403`) and `identityChangeReason` (5-500 chars, else `422 VALIDATION_ERROR`); the reason is stored append-only in `patient_identity_change` (V16) and never audited. V16 granted `patient:update-identity` to every role holding `patient:update`; since the owner decision of 2026-11-14 no default role template holds it (the default Receptionist has an explicit patient list without it, and V21 removes it from existing built-in RECEPTIONIST roles), so an administrator assigns it through a custom role. A field counts as changed only if its value differs, so resending an unchanged value needs no extra permission; a request that changes nothing writes nothing and keeps the version. `address` replaces the current address (the old one is kept with `is_current = false`); `emergencyContact` replaces the emergency contact. `abhaNumber` sets or changes the ABHA number (same encryption, hash and masking as registration; `409 DUPLICATE_ABHA` if another patient of the organization has it); `""` clears it. When the name, date of birth or phone changes, the `[E3-3]` duplicate rule runs again (excluding the patient itself) under the same UHID-counter lock as registration: candidates give `409 DUPLICATE_SUSPECTED` unless `confirmNotDuplicate=true` with `overrideReason` (needs `patient:override-duplicate`; recorded in `patient_duplicate_override`). Returns `200` with the full patient. Another organization's id is `404`. Audit (entity `PATIENT`, field names only, never values): `PATIENT_UPDATED` (changed fields, e.g. `phone`, `address.pincode`, `abhaNumber`), `PATIENT_IDENTITY_CHANGED` (identity field names + `identityChange.reason`), `PATIENT_DUPLICATE_OVERRIDDEN`.

**Implemented by `[E3-3]`: duplicate detection (BR-P3) and the "not a duplicate" override.** Rule (owner decision 2026-11-13): an existing, not `MERGED` patient of the caller's organization is a candidate if it has the same `dateOfBirth` and pg_trgm `similarity(fullName) >= duplicateDobThreshold` (default 0.45), or the same normalized phone (E.164, bare 10 digits get `+91`) and similarity `>= duplicatePhoneThreshold` (default 0.30); thresholds are organization settings (section 4). At most 10 candidates, best score first. `POST /patients` with candidates and without `confirmNotDuplicate=true` is `409 DUPLICATE_SUSPECTED` with `candidates: [{ id, uhid, fullName, dateOfBirth, phoneMasked, score }]` (`phoneMasked` keeps the `+91` prefix and the last 4 digits; `score` is the name similarity, 2 decimals; no ABHA, no address); nothing is written and no UHID is consumed. Retrying with `confirmNotDuplicate=true` and `overrideReason` (5-500 chars, trimmed; else `422 VALIDATION_ERROR`) registers the patient; this needs `patient:override-duplicate` (else `403`; held by the default Receptionist role and, through V15, every role that held `patient:create`). The override is stored append-only in `patient_duplicate_override` (patient, candidate ids, reason, user) and audited as `PATIENT_DUPLICATE_OVERRIDDEN` (entity `PATIENT`, field names `duplicateOverride.reason`, `duplicateOverride.candidateIds`; the free-text reason is never audited). Without candidates `confirmNotDuplicate` is ignored and nothing is recorded. An exact ABHA collision stays `409 DUPLICATE_ABHA`. Concurrency: the UHID counter row lock is taken before the duplicate query and held to commit, so registrations of an organization serialize and two simultaneous registrations of the same person give one `201` and one `409 DUPLICATE_SUSPECTED`. **`POST /patients/duplicate-check`** (`patient:create`): body `{ fullName, dateOfBirth, phone }` (all required, same formats as registration; a POST so the terms stay out of URLs), returns the candidate array (possibly empty), and writes one `PATIENT_DUPLICATE_CHECK` audit event with the candidate count only.
**Implemented by `[E3-2]`: `GET /patients`** (`patient:search`). Query: `q` (fuzzy name, min 3 chars: pg_trgm word similarity, so the query need only be close to part of the name, threshold 0.6, best match first; index-backed under row-level security, see database-design.md section 5), `uhid` (exact, case-insensitive), `phone` (normalized to E.164; a bare 10-digit number gets `+91`; spaces/hyphens ignored), `dob` (ISO date), `page`/`size` (default 0/20, max 100). Filters combine with AND; at least one is required, otherwise `422 VALIDATION_ERROR`. Returns the pagination envelope of `{ id, uhid, fullName, sex, dateOfBirth, phoneMasked, abhaLast4, status }` (owner decision 2026-11-13: `phoneMasked` keeps the `+91` prefix and last 4 digits, same format as the duplicate candidates, e.g. `+91******0001`; the full `phone` is returned only by `GET /patients/{id}`). `totalItems` is computed by a separate query and may differ slightly from the page under concurrent writes. Each search writes one `PATIENT_SEARCH` audit event carrying the result count (`audit_event.result_count`, V13) and no query terms. **`POST /patients/search-by-abha`** (`patient:search`, CSRF like any POST): body `{ "abhaNumber": "..." }` (14 digits, hyphens allowed; else `422`), `page`/`size` query params; exact match through the keyed hash (ADR-0009), organization-scoped, same response envelope and the same single `PATIENT_SEARCH` audit event with result count. ABHA is a POST body, never a query parameter, so it stays out of URLs and access logs (the dev proxy logs `$uri` only); ABHA values are never audited or logged.

**Implemented by `[E3-1]`: `POST /patients` and `GET /patients/{id}`** (update, contacts beyond the one emergency contact, allergies and timeline come later). `POST` returns `201` with the full patient: `{ id, uhid, fullName, sex, dateOfBirth, dobEstimated, phone, abhaLast4, address, emergencyContact, status, version, createdAt, updatedAt }` (`address` and `emergencyContact` are `null` when not supplied; both are optional, but if given every field except `address.line2` is required). `uhid` is `HMS-` plus the next number of the organization's gapless sequence, at least 6 digits (`HMS-000124`); it is allocated under a row lock inside the registration transaction, so a failed registration never leaves a gap. Give exactly one of `dateOfBirth` or `ageYears` (0-130, requires `dobEstimated=true`; stored as an estimated date of birth); anything else is `422 VALIDATION_ERROR`. A bare 10-digit phone is stored as `+91...`. Optional `abhaNumber` (`[E3-2]` follow-up, ADR-0009): 14 digits, optionally `NN-NNNN-NNNN-NNNN`; format check only, no checksum or ABDM verification. It is stored AES-256-GCM encrypted (key id per row; key id, organization id, patient id and field name bound as associated data, so a ciphertext copied to another row does not decrypt) with an HMAC-SHA256 lookup hash and its last 4 digits; responses carry only `abhaLast4` (`null` when none), never the number. A number already registered in the organization is `409 DUPLICATE_ABHA`. Audit records the field name `abhaNumber` only. Update ([E3-5]) will accept it too. `GET /patients/{id}` is audited (`PATIENT_VIEWED`); another organization's id is `404 NOT_FOUND`. Audit: `PATIENT_CREATED` (entity `PATIENT`, field names such as `fullName`, `address.city`, never values) and `PATIENT_VIEWED`.

Rules: fullName 2–120; sex ∈ {M,F,O,U}; dateOfBirth ≤ today or `ageYears` with `dobEstimated=true`; phone E.164 (India default +91, 10 digits); pincode 6 digits. Retry with `confirmNotDuplicate=true` records an override. Search returns minimal fields (no history, masked phone). A `fullName` or emergency-contact `name` shorter than 2 characters after trimming is `422 VALIDATION_ERROR`. `phone` search is exact; name is trigram word similarity (min 3 chars).

Implemented `[E5-1]` (`POST /appointments`, `GET /appointments/{id}`):
- Body `patientId`, `doctorId`, `startAt` (whole minute), `durationMinutes` (1-480), optional `reason` (≤500, never audited or logged), optional `outsideAvailability` (default false). Response adds `patientId`, `doctorId`, `durationMinutes`, `type` (`SCHEDULED`), `reason`, `outsideAvailability`, `createdAt`, `updatedAt`.
- Errors: `422 VALIDATION_ERROR` (missing/invalid fields); `422 START_IN_PAST` (past start without `appointment:backdate`); `422 DOCTOR_NOT_AVAILABLE` (unknown, other-org or inactive doctor); `422 PATIENT_NOT_AVAILABLE` (unknown or other-org patient); `422 OUTSIDE_AVAILABILITY` (not inside one weekly window, off its slot grid, or on leave); `403` for `outsideAvailability:true` without `appointment:override`; `409 SLOT_CONFLICT` on overlap with a SCHEDULED/CHECKED_IN/IN_CONSULTATION/COMPLETED appointment of the doctor.
- Audit: `APPOINTMENT_BOOKED` (field names), `APPOINTMENT_AVAILABILITY_OVERRIDDEN` when overridden, `APPOINTMENT_VIEWED` on detail.
- `GET /doctors/{id}/slots` now leaves out booked times (Q9).

Implemented `[E5-2]` (`GET /appointments`, `POST /appointments/{id}/reschedule|cancel|no-show`):
- States `SCHEDULED, CHECKED_IN, IN_CONSULTATION, COMPLETED, CANCELLED, NO_SHOW, RESCHEDULED`; allowed moves exactly as domain-model.md section 6 (`AppointmentStatus.canTransitionTo`); anything else is `409 INVALID_STATE_TRANSITION`. Every action sends the `version` the caller last saw; a stale one is `409 CONCURRENT_MODIFICATION` (checked before the transition). Unknown or other-organization ids are `404`.
- `POST /appointments/{id}/reschedule` `{version, startAt, durationMinutes}` (permission `appointment:update`; only from `SCHEDULED`): marks the old appointment `RESCHEDULED` (its time is freed, so the new slot may overlap it) and returns `201` with a new `SCHEDULED` appointment whose `rescheduledFromId` is the old id; patient, doctor and `reason` carry over. The new slot obeys the booking rules (`422 OUTSIDE_AVAILABILITY`, `422 START_IN_PAST` without `appointment:backdate`, `422 DOCTOR_NOT_AVAILABLE`, `409 SLOT_CONFLICT`); there is no availability override on a reschedule. On any error nothing changes. An appointment can be rescheduled once (it has one successor).
- `POST /appointments/{id}/cancel` `{version, reason}` (`appointment:cancel`; from `SCHEDULED` or `CHECKED_IN`): `reason` is required, 1-500 characters after trimming, else `422 VALIDATION_ERROR`. Returns `200` with `status: CANCELLED`, `cancelReason`, `cancelledAt`.
- `POST /appointments/{id}/no-show` `{version}` (`appointment:update`; from `SCHEDULED`): `200` with `status: NO_SHOW`. `CANCELLED`, `NO_SHOW` and `RESCHEDULED` free the doctor's time.
- `GET /appointments?doctorId=&patientId=&date=&status=&page=&size=` (`appointment:read`): all filters optional; `date` is a day in the organization's timezone; `status` one of the seven states else `422`; ordered by `startAt`; envelope `{items, page, size, totalItems}` (`size` max 100). Items are the detail representation (adds `rescheduledFromId`, `cancelReason`, `cancelledAt`, null when not applicable).
- Audit: `APPOINTMENT_RESCHEDULED` (old id) plus `APPOINTMENT_BOOKED` (new id), `APPOINTMENT_CANCELLED`, `APPOINTMENT_NO_SHOW`, `APPOINTMENT_LISTED` (filter names). Field names only; the reason text is never audited or logged.

Implemented `[E5-3]` (`POST /appointments/{id}/check-in`, `POST /appointments/walk-in`, `GET /queue`):
- `POST /appointments/{id}/check-in` `{version}` (`appointment:check-in`; from `SCHEDULED` only): `200` with the appointment, `status: CHECKED_IN`, `tokenNo` and `tokenDate`. The token is the next number (from 1) of that doctor and day; `tokenDate` is the check-in instant's date in the organization's time zone, so numbers restart each day and each doctor has their own. Concurrent check-ins get distinct, gapless numbers. A repeated check-in is `409 INVALID_STATE_TRANSITION`, a stale `version` `409 CONCURRENT_MODIFICATION`, an unknown or other-organization id `404`.
- `POST /appointments/walk-in` `{patientId, doctorId, reason?}` (`appointment:create`): `201` with `type: WALK_IN`, `status: CHECKED_IN`, a token, `startAt` = now rounded down to the minute and `durationMinutes` = the doctor's default slot length. A walk-in is not subject to availability and holds no slot (it never causes `SLOT_CONFLICT`, and does not remove a free slot). Errors: `422 VALIDATION_ERROR`, `422 DOCTOR_NOT_AVAILABLE` (unknown, other-org or inactive), `422 PATIENT_NOT_AVAILABLE`.
- `GET /queue?doctorId=&date=` (`appointment:read`; `doctorId` required, `date` defaults to today in the organization's zone): `{doctorId, date, items:[{appointmentId, patient:{id, uhid, name}, tokenNo, status}]}` ordered by `tokenNo`; only `CHECKED_IN` and `IN_CONSULTATION` appear (a finished, cancelled or no-show visit leaves the live queue). An unknown or other-organization `doctorId` is `404`; a doctor of the organization with nobody waiting gets an empty list.
- Appointment representations gain `tokenNo` and `tokenDate` (null until check-in). Internal port `appointment.api.AppointmentLifecycle` (`markInConsultation`, `markCompleted`) lets the clinical module move CHECKED_IN to IN_CONSULTATION to COMPLETED under the same state machine.
- Audit: `APPOINTMENT_CHECKED_IN` (field names `status`, `tokenNo`, `tokenDate`), for a walk-in after `APPOINTMENT_BOOKED`; `APPOINTMENT_QUEUE_VIEWED` (filter names). The walk-in `reason` is never audited or logged.

Implemented `[E5-4]` (appointments and queue UI; fix round 1):
- Every appointment representation (book, get, list, reschedule, cancel, no-show, check-in, walk-in) carries `patient: {id, uhid, name}` (UHID and name only, like the queue's patient). It is resolved with one batch lookup per response through the patient `api` port `PatientDirectory`; it writes no per-patient read audit (the appointment read/list audit still applies). `uhid`/`name` are null if the patient cannot be resolved.
- UI: `/appointments` (day view per doctor: free slots from `GET /doctors/{id}/slots` merged with `GET /appointments?doctorId&date&size=100`; book, walk-in, check-in with token, reschedule, cancel with reason, no-show) and `/queue` (polls `GET /queue` every 15 s). Both need `appointment:read`; each action button needs its own permission. `SLOT_CONFLICT` is shown inline in the booking dialog, `CONCURRENT_MODIFICATION` as a reload prompt.

Implemented `[E6-1]` (everything in the table above except `finalize` and `addenda`, which arrive with `[E6-2]`):

From an appointment: only the appointment's doctor (or a holder of `encounter:update-any`) may start it (`403` otherwise); the appointment must be `CHECKED_IN` (else `409 INVALID_STATE_TRANSITION`) and moves to `IN_CONSULTATION` in the same transaction; a second encounter for one appointment is refused. Ad hoc (`patientId`): the practitioner is the practitioner record linked to the signed-in user (`422 NOT_A_PRACTITIONER` when there is none); an unknown or other-org patient is `422 PATIENT_NOT_AVAILABLE`; neither id is `422 VALIDATION_ERROR`; an unknown appointment is `404`.
- `GET /encounters/{id}` (`encounter:read`) returns the same representation; `GET /patients/{id}/encounters?page&size` (`encounter:read`) returns the section 1 envelope of `{id, practitionerId, appointmentId, status, chiefComplaint, startedAt, finalizedAt}`, newest first; an unknown or other-org patient is `404`.
- Every `PUT` carries `version` (`422` if missing) and answers the full encounter with the new `version`; `409 ENCOUNTER_FINALIZED` for a finalized encounter, `409 CONCURRENT_MODIFICATION` for a stale version. Another doctor without `encounter:update-any` is `403`; another org's id is `404`.
- `PUT /observations` `{version, observations:[{kind, value:"120", unit}]}` (`observation:write`) replaces the whole set. Kinds and hard limits (outside: `422 VALIDATION_ERROR`, nothing stored): `BP_SYS` 0-300, `BP_DIA` 0-200, `PULSE` 0-300, `TEMP_C` 25-45, `SPO2` 0-100, `RESP_RATE` 0-80, `WEIGHT_KG` 0-500, `HEIGHT_CM` 0-272; at most 2 decimals; a kind at most once. Values outside the plausible range (`BP_SYS` 70-200, `BP_DIA` 40-130, `PULSE` 40-180, `TEMP_C` 35-41, `SPO2` 85-100, `RESP_RATE` 8-40) are stored and answered with `warnings:[{kind, message}]` (also on every later read). A role that holds `observation:write` but not `encounter:update` (nursing) may record vitals for any encounter of the organization; with `encounter:update` the treating-practitioner rule applies. Response: with `encounter:read` the full encounter (as `GET`); without it (nursing) a reduced `{id, version, observations, warnings}` only, so the write does not expose notes, diagnoses, plan, follow-up or chief complaint; no read audit is written for the reduced body (it holds only what the caller just wrote).
- `PUT /notes/{kind}` `{version, text}` (`encounter:update`; kind `SYMPTOMS|EXAMINATION|ASSESSMENT`, `ADDENDUM` is `422`; text 1-10000), `PUT /diagnoses` `{version, diagnoses:[{code?, description, primary}]}` (at most 20, at most one primary, empty list clears), `PUT /treatment-plan` `{version, text}`, `PUT /follow-up` `{version, date, instructions?}` (instructions at most 2000). Earlier note and diagnosis versions are kept in the database as history (`replaced_at`), never deleted.
- Permissions: the built-in DOCTOR role no longer holds `encounter:update-any` (V26 removes it from existing DOCTOR roles; the default template no longer grants it) so the treating-practitioner rule has teeth; it gains `observation:write`; NURSE is unchanged (PRD-exact template). Edit-any is for a custom role.
- Audit (field names only, never the text): `ENCOUNTER_STARTED` (`patientId`, `practitionerId`, `appointmentId`, `chiefComplaint`), `ENCOUNTER_OBSERVATIONS_UPDATED`, `ENCOUNTER_NOTE_UPDATED` (`notes.symptoms`...), `ENCOUNTER_DIAGNOSES_UPDATED`, `ENCOUNTER_TREATMENT_PLAN_UPDATED`, `ENCOUNTER_FOLLOW_UP_UPDATED`, `ENCOUNTER_VIEWED`, and `ENCOUNTER_HISTORY_VIEWED` against the patient (entity `PATIENT`). The appointment move writes no audit of its own. Internal ports: `clinical.api.EncounterQuery.find(orgId, encounterId)`, `practitioner.api.PractitionerDirectory`, `appointment.api.AppointmentLookup`.

**Implemented `[E6-2]`: finalize, addenda, database immutability.**
- `POST /encounters/{id}/finalize` `{version}` (`encounter:finalize`; treating practitioner or `encounter:update-any`): `200` with the full encounter, `status:"FINALIZED"`, `finalizedAt` set, `version` bumped. Order of checks: `404` (unknown or other-org id), `403` (not the treating practitioner), `409 ENCOUNTER_FINALIZED` (already finalized), `409 CONCURRENT_MODIFICATION` (stale version), `422` (no version). In one transaction it marks the appointment `COMPLETED` through `AppointmentLifecycle.markCompleted` (ad hoc encounters have no appointment and skip this; an appointment that is not `IN_CONSULTATION` is `409 INVALID_STATE_TRANSITION` and nothing is finalized), audits `ENCOUNTER_FINALIZED` (`status`, `finalizedAt`) and publishes the Spring event `clinical.api.EncounterFinalized` (ids and timestamp only).
- `POST /encounters/{id}/addenda` `{text}` (`encounter:addendum`; same treating-practitioner rule): `201` with the full encounter, the addendum appended to `notes` with `kind:"ADDENDUM"`. Only a FINALIZED encounter accepts one (else `409 INVALID_STATE_TRANSITION`); text 1-10000 (`422`). The encounter `version` does not change (the row is immutable). Addenda accumulate and are never edited or removed. Audit `ENCOUNTER_ADDENDUM_ADDED` (field `addendum`, never the text).
- Every edit endpoint of this section on a FINALIZED encounter answers `409 ENCOUNTER_FINALIZED`; the database enforces the same (V27/V35, `database-design.md` section 20h): SQLSTATE `HM005` from the guard is mapped to `409 ENCOUNTER_FINALIZED` by `ProblemDetailsHandler`.

Rules: ≥1 item; drugName, dose, frequency, durationDays (1–365) mandatory; allergy match produces `allergyWarnings` (non-blocking; issuing requires `acknowledgeAllergyWarnings=true`).

**Implemented `[E6-3]`: prescriptions with allergy warnings.** (`GET /prescriptions/{id}/pdf` follows in `[E6-5]`, below.)
- `POST /encounters/{id}/prescriptions` (`prescription:create`): `201` with an empty `DRAFT` (`versionNo` 1, `version` 0). Allowed on an `OPEN` or a `FINALIZED` encounter. An encounter has at most one live (DRAFT or ISSUED) prescription: a second one is `409 INVALID_STATE_TRANSITION` (revise instead). Audit `PRESCRIPTION_CREATED`.
- `PUT /prescriptions/{id}` `{version, items}` (`prescription:create`): replaces the whole item list of a DRAFT, `200`, `version` bumped. Order of checks: `422` (no version), `404`, `403`, `409 INVALID_STATE_TRANSITION` (not a DRAFT), `422 VALIDATION_ERROR` with `errors:[{field,code,message}]` (BR-C3: `drugName`, `dose`, `frequency`, `durationDays` 1-365 required; 1-50 items; field names like `items[0].dose`; the message never echoes the text), `409 CONCURRENT_MODIFICATION`. Audit `PRESCRIPTION_ITEMS_UPDATED` (field `items`).
- `POST /prescriptions/{id}/issue` `{version, acknowledgeAllergyWarnings?}` (`prescription:issue`): DRAFT to ISSUED (`issuedAt`, `issuedBy`). No items is `422 VALIDATION_ERROR`; with allergy warnings and without `acknowledgeAllergyWarnings:true`, `422 ALLERGY_NOT_ACKNOWLEDGED`. A non-DRAFT is `409 INVALID_STATE_TRANSITION`. Audit `PRESCRIPTION_ISSUED` (`status`, `issuedAt`, `issuedBy`, plus `acknowledgeAllergyWarnings` when warnings existed).
- `POST /prescriptions/{id}/revise` (`prescription:issue`, no body): only an ISSUED prescription (else `409 INVALID_STATE_TRANSITION`); it becomes `SUPERSEDED` and a new `DRAFT` copy is returned (`201`, `versionNo` + 1, `supersedesId`, items copied). The old one stays readable. Audit `PRESCRIPTION_REVISED` against the new id.
- `GET /prescriptions/{id}` (`prescription:read`): any holder, `PRESCRIPTION_VIEWED` audited. Response: `id, encounterId, patientId, status, versionNo, supersedesId, issuedAt, issuedBy, version, items[], allergyWarnings[]`.
- Write rule (as encounters): the treating practitioner of the encounter, or a holder of `encounter:update-any`; others get `403`. Unknown or other-org ids are `404`.
- Allergy warnings (`PUT`, `GET`, `issue`): the patient's active allergies (entries entered in error excluded) come from `patient.api.PatientAllergies.activeAllergies`; a warning is `{substance, severity}`, raised when the lower-cased `drugName` and the substance contain one another; one per substance, in recording order. Never audited.
- Database: V28 refuses changes to an issued prescription and its items (SQLSTATE `HM003`, mapped to `409 INVALID_STATE_TRANSITION`); see `database-design.md` section 20i.

**Implemented `[E6-5]`: prescription PDF.** (library: ADR-0017, OpenPDF)
- `GET /prescriptions/{id}/pdf` (`prescription:read`): `200 application/pdf` (`Content-Disposition: inline`, file name `prescription-<UHID>-v<versionNo>.pdf`). Only an `ISSUED` or `SUPERSEDED` prescription is printable; a `DRAFT` is `409 INVALID_STATE_TRANSITION`; unknown or other-org id `404`. Content: organization name and address, patient name and UHID, doctor name and registration no. (council in brackets), issue date (organization time zone), one row per item, and the text `SUPERSEDED` as a diagonal watermark on a superseded one. Internal ids are never printed; the data comes through the `organization`, `patient` and `practitioner` api ports.
- Audit `PRESCRIPTION_PDF_GENERATED` (fields `status`, `versionNo`), same transaction; no clinical values.

**Implemented `[E6-6]`: consultation UI.**
- Route `/consult/:id` (`encounter:read`). Queue rows: `Start consult` (checked-in, `encounter:create`, `POST /encounters {appointmentId}`) and `Resume consult` (in consultation, `encounter:read`; finds the OPEN encounter of that appointment through `GET /patients/{id}/encounters`).
- Sections and the permission each save needs: vitals `observation:write`, notes/diagnoses/plan/follow-up `encounter:update`, prescription `prescription:create` (draft, items) and `prescription:issue` (issue, revise), finalize `encounter:finalize`, addendum `encounter:addendum`, PDF link `prescription:read`. Plausibility `warnings[]` are shown non-blocking; hard limits (`422`) show the message; prescription `422` field errors (`items[i].field`) show beside the field; issue is blocked in the UI until `allergyWarnings` are acknowledged (`acknowledgeAllergyWarnings:true`). A `403` on a write is shown as the treating-practitioner rule. FINALIZED: all inputs read-only, addenda stay possible.
- Prescription lookup: every full encounter representation (`GET /encounters/{id}`, start, and the PUT/finalize/addenda responses) carries `prescriptions: [{id, status, versionNo}]`, newest first, superseded ones included (read from the `clinical` tables, no extra module call). It is filled only for callers holding `prescription:read`; for others it is `[]`. The reduced PUT observations body (callers without `encounter:read`) never contains it. The UI works on the first DRAFT or ISSUED entry, refetches the encounter after create/revise, and shows "A prescription already exists for this visit" (then reads it) when create answers `409`.

**Implemented `[E7-1]`: invoice drafts and calculations.** `POST /invoices { type:"OPD", patientId, encounterId }` -> `201` DRAFT with zero totals; the encounter must exist in the organization (`404`) and belong to the patient (`422 VALIDATION_ERROR`); an unknown patient is `404`; `IPD` is `422` until admissions exist; a second live invoice for the encounter is `409 INVALID_STATE_TRANSITION`. Response `{ id, type, patientId, encounterId, admissionId, status, invoiceNo, issuedAt, subtotal, discountTotal, taxTotal, total, version, items:[{ id, serviceId, description, quantity, unitPrice, discount, discountReason, taxRate, gross, taxable, tax, total }], createdAt, updatedAt }`; every amount, `quantity` and `taxRate` is a 2-place decimal string. `GET /invoices ?patientId,status,from,to,page,size` (newest first, pagination envelope, `items` empty per row); `GET /invoices/{id}` (audited `INVOICE_VIEWED`). `PUT /invoices/{id}/items { version, items:[{ serviceId?, description?, quantity, unitPrice?, discount?, discountReason?, taxRate? }] }` replaces all lines (1-100) of a DRAFT: with `serviceId` the line is priced from the catalog price valid now and `description` defaults to the service name; `unitPrice` different from that price, or a line without `serviceId` (then `description` and `unitPrice` are required), needs `invoice:price-override` (`403`). Line rules: quantity 0.01-9999 and tax rate 0-100 with at most 2 places, discount 0..gross; violations are `422 VALIDATION_ERROR` with `errors[].field` like `items[0].quantity`. Calculation: `gross = round(quantity x unitPrice)`, `taxable = gross - discount`, `tax = round(taxable x taxRate / 100)`, `total = taxable + tax` (HALF_UP per line); invoice totals are the sums of the line amounts. `POST /invoices/{id}/discard { version }` -> DISCARDED (frees the encounter). Changes to a non-DRAFT invoice are `409 INVOICE_IMMUTABLE`; stale `version` is `409 CONCURRENT_MODIFICATION`. Audit (field names only): `INVOICE_CREATED`, `INVOICE_ITEMS_UPDATED`, `INVOICE_DISCARDED`, `INVOICE_VIEWED`. The payment module uses `com.hms.billing.api.InvoiceBalancePort` (`lockForPayment` = row lock, `applyPaymentStatus` among ISSUED/PARTIALLY_PAID/PAID).

**Implemented `[E7-8]`: discounts with reason and permission.** A line with `discount` > 0 needs the permission `invoice:discount` (`403` otherwise; field validation `422` is answered first) and a non-blank `discountReason` of at most 200 characters (`422 VALIDATION_ERROR`, `errors[].field` `items[i].discountReason`); a zero discount needs neither and any reason sent with it is dropped. A discount above its line amount is `422 BUSINESS_RULE_VIOLATION` (`errors[].field` `items[i].discount`). `PUT /invoices/{id}/discount { version, percent, reason }` (permission `invoice:discount`) on a DRAFT: `percent` is a decimal string 0-100 with at most 2 places, `reason` is required (1-200); each line gets `discount = round_half_up(gross x percent / 100)` and the reason (lines whose discount is 0.00 get none), existing line discounts are replaced, and the lines are recalculated by the calculator above. Invalid `percent`/`reason` -> `422 VALIDATION_ERROR`; no items -> `422 BUSINESS_RULE_VIOLATION`; non-DRAFT -> `409 INVOICE_IMMUTABLE`; stale `version` -> `409 CONCURRENT_MODIFICATION`; another organization's id -> `404`. `unitPrice x quantity`, a line total including tax, and the invoice subtotal/total are capped at `999999999999.99` (NUMERIC(14,2)): beyond it the response is `422 VALIDATION_ERROR` with `items[i].unitPrice` (line) or `items` (invoice), never `500`. Audit (field names only, never the reason): `INVOICE_DISCOUNT_APPLIED` on the percent endpoint and on an items update that carries a discount. The default `ACCOUNTANT` role holds `invoice:discount` (`V30`).

**Implemented `[E7-2]`: issue invoices with gapless numbers.** `POST /invoices/{id}/issue` (permission `invoice:issue`, no body) requires the header `Idempotency-Key` (1-200 printable characters without spaces; missing or invalid -> `422 VALIDATION_ERROR`, `errors[].field` `Idempotency-Key`). In one transaction: the invoice row is locked, it must be DRAFT (`409 INVOICE_IMMUTABLE` otherwise) with at least one item (`422 BUSINESS_RULE_VIOLATION`), the totals are recomputed from the stored lines, and the `INVOICE` number is allocated last from `document_sequence` with period `FY2026-27` (April-March in the organization's time zone) and formatted `2026-27/000031`; status becomes ISSUED with `issuedAt`/`issuedBy`. Response `200` with the invoice as above. Numbers are gapless per organization and financial year: a rolled-back issue returns its number. Audit `INVOICE_ISSUED` (field names only); event `com.hms.billing.api.InvoiceIssued(organizationId, invoiceId, patientId, invoiceNo, total, issuedAt)` is published in the transaction. Idempotency (shared by payments and refunds, `com.hms.shared.web.idempotency.IdempotencyService`): records are keyed by (organization, route template, key); a replay of the same key and request returns the stored status and body without a second number; the same key with a different request (another invoice id, or another body) is `422 IDEMPOTENCY_KEY_REUSED`; only successful responses are stored, so a failed request may be retried with the same key. After issue every change to the invoice or its items is refused (`409 INVOICE_IMMUTABLE`; database SQLSTATE `HM004`) except the payment status and `CANCELLED`.

**Implemented `[E7-3]`: partial, idempotent, row-locked payments.** `POST /invoices/{id}/payments { amount, mode, referenceNo? }` (permission `payment:create`) requires `Idempotency-Key` (as for issue; the request hash covers the invoice id, amount, mode and referenceNo, so another invoice or body under the same key is `422 IDEMPOTENCY_KEY_REUSED`). `amount` is a decimal string > 0 (a JSON number is `400`); `mode` is `CASH|CARD|UPI|BANK_TRANSFER|CHEQUE`; `referenceNo` 1-50 characters; violations are `422 VALIDATION_ERROR`. In one transaction: idempotency lock, the invoice row lock (billing's `InvoiceBalancePort.lockForPayment`; unknown or other-organization id -> `404`), status must be ISSUED or PARTIALLY_PAID (`409 INVALID_STATE_TRANSITION`, also for DRAFT and PAID), `outstanding = total - paid + refunded` with paid and refunded summed from the payment module's own tables, `amount > outstanding` -> `409 EXCEEDS_OUTSTANDING` with detail `Outstanding is X.`; the `RECEIPT` number is allocated last (`RCT-2026-27/000044`, financial year in the organization's time zone); the invoice becomes PARTIALLY_PAID or PAID. Response `201 { id, invoiceId, amount, mode, referenceNo, receiptNo, receivedAt, receivedBy, outstanding, invoiceStatus }`; a replay returns the stored response and records nothing. Audit `PAYMENT_RECORDED` (field names only; includes `invoice.status` when it changed). Payments are append-only. `GET /payments ?from,to,mode,page,size` (permission `payment:read`; `from` inclusive and `to` exclusive on `receivedAt`; newest first; size 1-100) returns the pagination envelope of `{ id, invoiceId, amount, mode, referenceNo, receiptNo, receivedAt, receivedBy }`.

**Implemented `[E7-4]`: refunds with approval and credit notes.** `POST /payments/{id}/refunds { amount, reason, mode }` (permission `refund:create`) requires `Idempotency-Key` (hash covers payment id, amount, mode and reason). `amount` > 0 decimal string, `mode` as for payments, `reason` 1-500 characters (`422 VALIDATION_ERROR`). In one transaction: idempotency lock, payment lookup (unknown or other-organization id -> `404`), the payment's invoice row lock, `amount <= payment.amount - sum of non-rejected refunds` else `422 REFUND_EXCEEDS_PAID` (detail `Refundable is X.`), the `REFUND` number last (`RF-2026-27/000001`). Amounts up to `hms.billing.refund-approval-threshold` (default `1000.00`, env `HMS_REFUND_APPROVAL_THRESHOLD`) are `RECORDED`; larger ones are `PENDING_APPROVAL`. `POST /refunds/{id}/approve` (no body) and `POST /refunds/{id}/reject { reason }` (permission `refund:approve`) decide a pending refund: the requester gets `403 SELF_APPROVAL_FORBIDDEN`, a refund that is not pending `409 INVALID_STATE_TRANSITION`; approve makes it `RECORDED`, reject `REJECTED` (frees the amount). Response `{ id, paymentId, invoiceId, amount, mode, refundNo, status, requestedAt, requestedBy, decidedAt, decidedBy, invoiceStatus }` (`201` on create, `200` on decisions; the reason is not echoed). Only RECORDED refunds count as refunded; when one becomes effective the invoice status is recomputed (`PAID` -> `PARTIALLY_PAID` -> `ISSUED` when net paid reaches 0). Audit `REFUND_REQUESTED` / `REFUND_APPROVED` / `REFUND_REJECTED` (field names only). `POST /invoices/{id}/credit-notes { amount, reason }` (permission `invoice:credit`; no Idempotency-Key) on ISSUED, PARTIALLY_PAID or PAID (`409 INVALID_STATE_TRANSITION` otherwise): the invoice row is locked, `sum of credit notes <= total` else `422 CREDIT_EXCEEDS_TOTAL`, the `CREDIT_NOTE` number is allocated last (`CN-2026-27/000001`). When the credit notes reach the total and the invoice is ISSUED (net paid 0) it becomes `CANCELLED`. Response `201 { id, invoiceId, amount, creditNoteNo, issuedAt, issuedBy, creditedTotal, invoiceStatus }`; audit `CREDIT_NOTE_ISSUED` (field names only). Credit notes reduce what may be paid: payment outstanding is `total - credited - paid + refunded` (`InvoiceBalance.credited` from billing.api). Refunds, refund decisions and credit notes are append-only. `GET /refunds` is not implemented yet.

**Implemented `[E7-5]`: invoice and receipt PDFs.** `GET /invoices/{id}/pdf` (permission `invoice:read`) returns `application/pdf` (inline, file name `invoice-<invoiceNo>.pdf` with `/` as `-`) for an invoice that has been issued (ISSUED, PARTIALLY_PAID, PAID, CANCELLED); a DRAFT or DISCARDED invoice is `409 INVALID_STATE_TRANSITION`, an unknown or other-organization id `404`. It prints the organization name and address, invoice number, issue date (organization time zone), patient name and UHID, the lines (description, quantity, unit price, discount, tax, total) and a summary with exactly the API's money strings for subtotal, discount, tax and total, then credit notes, paid, refunded and outstanding, where `outstanding = total - credited - paid + refunded`; a CANCELLED invoice carries a `CANCELLED` watermark. Paid and refunded come from the payment module through billing's port `com.hms.billing.api.InvoicePaymentTotals` (implemented in payment; billing does not depend on payment). `GET /payments/{id}/receipt` (permission `payment:read`) returns the receipt PDF (`receipt-<receiptNo>.pdf`): receipt number, invoice number (via `com.hms.billing.api.InvoiceLookup`), date, patient name and UHID, amount, mode and reference; unknown or other-organization id `404`. Internal ids are never printed. Both endpoints declare `produces: application/pdf`; an error still answers as `application/problem+json` (a draft with `Accept: application/pdf` is `409`, not `406`). Audit `INVOICE_PDF_GENERATED` (fields `status`, `invoiceNo`) and `RECEIPT_PDF_GENERATED` (fields `receiptNo`, `invoiceId`), field names only.

**Implemented `[E7-7]`: nightly reconciliation.** `billing.application.ReconciliationJob` runs at 02:30 Asia/Kolkata (`hms.billing.reconciliation-cron`, env `HMS_RECONCILIATION_CRON`, `-` disables) with no user session: for each ACTIVE organization it sets the organization context (`OrganizationContext.runAs`, normal `hms_app` role and RLS) and checks every issued invoice against `hms.invoice_reconciliation_v` (database-design 20o lists exactly what is flagged). Each mismatch logs ERROR with invoice id and organization id only, increments the Micrometer counter `hms.billing.reconciliation.mismatch` (Prometheus `hms_billing_reconciliation_mismatch_total`) and writes audit `RECONCILIATION_MISMATCH` (entity `INVOICE`, null system actor, field names `status`, `netPaid`, `creditedTotal`). Mismatches are re-reported every night until corrected (by credit note or refund; data is never edited). Operations: alert on `increase(hms_billing_reconciliation_mismatch_total[1d]) > 0`; no Prometheus rules file exists in `infra/monitoring` yet, so the rule is not wired.

**Implemented `[E7-6]`: billing UI.** Routes `/invoices` (`invoice:read`; issued and partly paid invoices from `GET /invoices?status=ISSUED,PARTIALLY_PAID`) and `/invoices/:id` (`invoice:read`). `GET /invoices` `status` now accepts several statuses separated by commas (each must be a known status, else `422`; one value works as before). Entry point: a **Billing** section at the bottom of the consultation screen (`invoice:read` / `invoice:create`): "Create invoice" (`POST /invoices {type:"OPD", patientId, encounterId}`) or a link to the encounter's live invoice (found with `GET /invoices?patientId=`, ignoring DISCARDED and CANCELLED; a `409` from create shows "An invoice already exists for this visit"). Editor (DRAFT, `invoice:update`): catalog picker (`GET /services?active=true`, `catalog:read`; services without a price are disabled), lines sent without `unitPrice` unless the user edited the price (so the catalog price applies; a changed price or a custom line needs `invoice:price-override`, a `403` is worded as such), line discounts only for `invoice:discount` with a required reason, percent discount (`PUT /discount`), save (`PUT /items`; the totals shown are always the server's response), discard, issue (`invoice:issue`, disabled while there are unsaved changes). Payments (`payment:create`, ISSUED or PARTIALLY_PAID): amount, mode, reference; the result shows the server's `outstanding`, status and the receipt PDF link (`payment:read`). Money, quantity and rate are strings end to end: the client only checks their shape by pattern (`^\d{1,12}(\.\d{1,2})?$` for amounts) and never converts them to numbers; whether a payment exceeds the outstanding amount is the server's `409 EXCEEDS_OUTSTANDING` ("Outstanding is X."). `Idempotency-Key`: one UUID per click-intent; it is reused for the same request (automatic retry of a network failure, or a manual retry after an error) and replaced after success or when the payment's invoice/amount/mode/reference changes. Known gaps: invoice responses carry no `outstanding` and no patient name (the list shows invoice no., status and total; outstanding is shown only in the payment result), and there is no per-invoice payment list (receipts are linked for payments taken on the screen).

## 14. Audit (admin)
`GET /audit-events` ?actorId,entityType,entityId,patientId,action,from,to · `audit:read` (System Administrator, Facility Administrator). Read of audit events is itself audited.

**Implemented by `[E1-9]`**: `GET /audit-events` `?actorId=<uuid>&action=<UPPER_SNAKE>&entityType=<UPPER_SNAKE>&entityId=<uuid>&from=<UTC instant>&to=<UTC instant>&page=0&size=50` (size 1-100), permission `audit:read` (held by the default System Administrator and Facility Administrator; V11 backfilled existing Facility Administrator roles). All filters are optional and combine with AND; `from`/`to` are inclusive ISO-8601 UTC instants (`2026-01-31T00:00:00Z`) and `from` must not be after `to`. Malformed values, a reversed range or a non-numeric or out-of-range page/size are `422 VALIDATION_ERROR`. Results are the section 1 envelope, newest first (`occurredAt`, then id, descending), rows `{ id, occurredAt, actorId, action, entityType, entityId, outcome, changedFields, correlationId, changedValues }` (exactly what is stored: field names, never values, except `changedValues: [{ field, oldValue, newValue }]` for the ADR-0016 allowlist of code fields: `APP_USER.status`, `APP_USER.roles`, `ROLE.permissions`, set values as sorted comma-separated codes, usually empty; `actorId`/`entityId`/`correlationId` may be `null`). `audit_event` is outside RLS, so the query always carries an explicit `organization_id = <principal org>` predicate; the organization is never a parameter (an `organizationId` parameter is ignored) and another organization's events never appear. There is no path-id endpoint, so no cross-org 404 case applies. `patientId` is not supported yet (the table has no patient column; filter `entityType=PATIENT&entityId=<id>` for patient-entity events). Every successful query is audited as `AUDIT_VIEWED` (entity `AUDIT_EVENT`, no entity id) in the same transaction, with `changedFields` holding the names of the filters used (`action`, `entityId`, `from`...), never their values; rejected requests write nothing. The time range is on the partition key `occurred_at` (partition pruning); ordering uses `ix_audit_event_org_time`. UI: `/audit` (nav entry "Audit", route guarded by `audit:read`) with the six filters and a paged table.
