# ADR-0001: Modular monolith (vs microservices)
- **Status:** Accepted (2026-11-07, owner) — boundary verification with ArchUnit only; Spring Modulith deferred
- **Context:** Solo developer, 50 users, one facility, strong transactional needs across bed/admission/billing.
- **Problem:** Choose the deployment/structure style that keeps invariants simple and ops minimal while allowing later extraction.
- **Options:** (A) Microservices; (B) Modular monolith; (C) Layered monolith without enforced boundaries.
- **Decision:** B. One deployable, one DB. Modules expose an `api` package; others may only depend on it. Boundaries verified in CI by ArchUnit rules in the `architectureTest` source set (ADR-0013): no module imports another module's non-`api` packages, no cyclic module dependencies, `@Transactional` only in `application`, every controller endpoint has `@PreAuthorize`. Reporting reads views (documented exception). Spring Modulith is deferred: revisit only if its module events, event publication registry or generated module docs become needed, via a new ADR.
- **Consequences:** + local transactions, simple ops, easy refactor. + ArchUnit is test-scope only: no runtime dependency, no framework conventions imposed on package layout. − Discipline required; shared DB makes later extraction need data separation work. − Module rules are hand-written and must be kept in sync when modules are added.
- **Extraction path (if a real need ever arises):** extract one module at a time, never a big-bang split. Easy: reporting (needs a read replica/pipeline instead of views), notifications, ABDM adapter (already behind an outbox, ADR-0011). Medium: appointment, patient. Keep together permanently: admission + bedmanagement + billing + payment, whose invariants depend on one local transaction and the lock order bed → admission → invoice; splitting them would require sagas with compensation and would weaken same-transaction audit (ADR-0007). Main costs of any extraction: splitting the shared schema (ADR-0003), replacing in-process `api` calls with remote calls/events, and the added ops burden. At R1 scale (~50 users, one facility) vertical scaling suffices; for Stage 3 SaaS, prefer more monolith instances over service extraction.
