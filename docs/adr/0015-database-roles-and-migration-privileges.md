# ADR-0015: Database roles and migration privileges
- **Status:** Accepted (2026-11-09, owner)
- **Context:** `[E0-6]` requires that the application's database role cannot run DDL. Today the app and Flyway share one login (in Compose, the Postgres superuser). ADR-0010 (Proposed) also needs a non-owner app role without `BYPASSRLS` if RLS is adopted, and the immutability rules (ADR-0007, ADR-0012) rely on the app lacking `UPDATE`/`DELETE` on append-only tables.
- **Options:** (A) one role for everything (status quo); (B) owner role for Flyway + DML-only app role, roles provisioned outside Flyway; (C) as B but roles created by a Flyway migration (needs `CREATEROLE` for the migrator and passwords in migrations or placeholders); (D) migrations run as a separate job/container instead of at app startup.
- **Decision:** B. `hms_owner` owns the database, schema `hms` and every object and is used only by Flyway (`spring.flyway.user`, env `HMS_DB_MIGRATION_*`). `hms_app` is the runtime login (`HMS_DB_*`): `USAGE` on `hms`, default `SELECT/INSERT/UPDATE` on tables, no `DELETE` by default, no `CREATE`/`TEMP`, `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS`. Roles and passwords are created by a provisioning script (Compose init script, Testcontainers init script, operator runbook), never by migrations. Flyway keeps running in-process at startup; D is deferred until a deployment needs it. Detail: `docs/architecture/database-design.md` section 3.
- **Consequences:** + DDL and privilege escalation from the app are impossible; RLS can be enforced later without role changes; append-only rules hold at the privilege level. − Two credentials to manage per environment; existing dev volumes must be recreated once; the app process still holds owner credentials at startup (acceptable for R1; option D removes this).
