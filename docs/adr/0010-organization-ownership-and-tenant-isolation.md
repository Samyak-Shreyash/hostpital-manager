# ADR-0010: Organization ownership and tenant isolation
- **Status:** Accepted (2026-11-12, owner) — **deviates from charter ("tenant_id")**: naming follows master prompt (`organization_id`)
- **Context:** Master prompt: all business rows reference an organization; "organization_id alone is not isolation."
- **Decision:** (1) `organization_id NOT NULL` + FK on every business table; (2) composite same-org FKs for high-risk relations; (3) every repository query is org-scoped via a mandatory `OrganizationContext` (derived from the authenticated principal, never from request params); (4) PostgreSQL RLS with `FORCE ROW LEVEL SECURITY` and per-transaction `SET LOCAL app.organization_id`, app DB role without BYPASSRLS; (5) automated isolation test suite (two orgs, every endpoint returns 404 for cross-org ids). Facility-level (`facility_id`) is deferred.
- **Consequences:** + defence in depth. − Slight complexity with pooling/`SET LOCAL`; RLS can mask bugs (queries return empty) so tests are explicit. **Even so, this is single-organization deployment in R1; do not market it as multi-tenant isolation until Stage 3 hardening and review.** If RLS proves disproportionate for the solo timeline, fall back to (1)–(3)+(5) and record the downgrade.
- **Spike outcome `[E1-2]` (2026-11-12): keep RLS, no downgrade.** Verified against PostgreSQL 17 as `hms_app` through HikariCP, Spring transactions and Hibernate (`backend/src/integrationTest/java/com/hms/shared/db/RowLevelSecurityFeasibilityIT.java`): a transaction sees and writes only its own org's rows; a missing context returns zero rows (fail-closed); the context does not survive commit **or** rollback on a reused pooled connection; JPA native queries run on the connection carrying the context. Rules for `[E1-6]`:
  - Set the context with `SELECT set_config('app.organization_id', :org, true)` (transaction-local; `SET LOCAL` cannot take a bind parameter) as the first statement of every application-service transaction, from `OrganizationContext`. Never use `is_local = false`: a session-level value leaks to the next borrower of the connection (the test demonstrates this).
  - Policies must read `NULLIF(current_setting('app.organization_id', true), '')::uuid`. After a custom setting has been used on a connection it reads back as `''`, not `NULL`, and `''::uuid` errors instead of hiding rows.
  - Every RLS table: `ENABLE` + `FORCE ROW LEVEL SECURITY`, one policy with both `USING` and `WITH CHECK`. FORCE also binds `hms_owner`, so migrations that seed or backfill business rows must set the context per org.
  - A cross-org write raises SQLSTATE `42501`. Spring maps it to `BadSqlGrammarException`, so app-level scoping (point 3) must stop it first. Reaching RLS is a bug, to be logged and answered with `404`, never `500` detail.
  - Not covered by the spike, so `[E1-6]` must cover it: background jobs and `@Scheduled` tasks (e.g. audit partition maintenance) run without a user and must set or deliberately omit the context; and reporting views (ADR-0001 exception) must be `security_invoker` so RLS applies.
