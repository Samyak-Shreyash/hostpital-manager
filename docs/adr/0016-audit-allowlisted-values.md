# ADR-0016: Old/new values for allowlisted non-PHI audit fields
- **Status:** Accepted (2026-11-17, owner: "Non-PHI values only", UI issue A5)
- **Context:** Administrators reading the audit log (UI issue A5) can see that a user's `roles` or a role's `permissions` changed, but not to what. ADR-0007 and PRD AUD-4 record field *names* only so that passwords, tokens, clinical free text and PHI can never reach the audit table.
- **Decision:** Amend ADR-0007: an audit event may also carry old/new values, but only for fields on a central allowlist in `com.hms.audit.api.AuditValueChange.ALLOWED`, and only as code values. The initial allowlist is `APP_USER.status`, `APP_USER.roles` (role codes) and `ROLE.permissions` (permission codes). Names, emails, phone numbers, free text and every patient/clinical/financial field stay names-only. Values are restricted to code characters (`[A-Za-z0-9_:,.-]`, at most 2000), set-valued fields are stored as sorted comma-separated codes, and a value may only be given for a field also listed in `changedFields`. Stored in `audit_event.changed_values` (jsonb array of `{field, old, new}`, V22) with a check constraint that admits only code characters. Returned by `GET /audit-events` as `changedValues`.
- **Options rejected:** full before/after snapshots (Envers-like; PHI duplication, rejected in ADR-0007); values for every non-clinical field (names and emails are personal data under DPDP with no audit need); a separate history table per entity (more schema for the same three fields).
- **Consequences:** + administrators see exactly which access was granted or removed. − Adding a field to the allowlist is a privacy decision: it needs review against this ADR, and must never include PHI or free text. The append-only and same-transaction rules of ADR-0007 are unchanged.
