## 2. Conventions (apply to every migration from V1)
- **Schema:** everything lives in `hms` (ADR-0003). Nothing is created in `public`. Objects are always schema-qualified in migrations.
- **Names:** `snake_case`; tables singular (`patient`, `invoice_item`); constraints `pk_<table>`, `fk_<table>_<ref>`, `uq_<table>_<cols>`, `ck_<table>_<rule>`, `ex_<table>_<rule>`; indexes `ix_<table>_<cols>`; triggers `trg_<table>_<purpose>`.
- **Standard columns** on business tables:
  | Column | Type | Notes |
  |---|---|---|
  | `id` | `uuid` PK | UUIDv7 generated by the app (ADR-0004); **no DB default** |
  | `organization_id` | `uuid NOT NULL` | FK to `organization` once it exists (section 4) |
  | `created_at`, `updated_at` | `timestamptz NOT NULL` | UTC; set by the app from the injected `Clock`, not `now()` defaults, so tests control time |
  | `version` | `bigint NOT NULL DEFAULT 0` | optimistic locking (`@Version`) on mutable aggregates only; immutable/append-only tables omit it |
- **Types:** money `NUMERIC(14,2)` (ADR-0012, Proposed — the type itself is confirmed in CLAUDE.md section 5); instants `timestamptz`; dates `date`; enums as `text` + `CHECK (col IN (...))` (not PG enums — adding values to a PG enum cannot run inside a transaction and is awkward to reverse); free text `text` (no arbitrary `varchar(n)`; length limits live in Bean Validation, plus a `CHECK (char_length(...))` where a hard limit matters).
- **No hard deletes** of clinical or financial data: lifecycle `status` columns instead (CLAUDE.md section 5).
- **Flyway:** forward-only `V<n>__<description>.sql` in `backend/src/main/resources/db/migration` (ADR-0013). A merged migration is never edited; fixes are new migrations. No `undo` scripts. One migration = one logical change, runs in a single transaction (avoid `CREATE INDEX CONCURRENTLY` unless the migration is marked non-transactional and reviewed).

## 3. Roles and privileges (ADR-0015, Accepted)
Two roles with separate credentials. The application **never** connects with DDL rights.

| Role | Login | Purpose | Privileges |
|---|---|---|---|
| `hms_owner` | yes (used only by Flyway) | Owns the database, schema `hms` and all objects; runs migrations | Owner of all objects. Not superuser in staging/prod |
| `hms_app` | yes (runtime datasource) | Application runtime | `CONNECT` on db; `USAGE` on `hms`; DML per table as granted below. **No** `CREATE` on db or any schema, no `TEMP`, not owner of anything, `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS` |

**Who creates the roles.** Roles are cluster-level and need passwords, so they are **provisioned outside Flyway** (no secrets in migrations):
- Compose dev stack: an init script mounted into the Postgres container's `/docker-entrypoint-initdb.d/` creates `hms_owner` (owner of the `HMS_DB_NAME` database) and `hms_app` from env vars. Runs only on an empty volume — existing dev volumes must be recreated once (`docker compose ... down -v`).
- Testcontainers / CI: the same script via `withInitScript`/`withCopyFileToContainer`, so tests exercise the real grants.
- Staging/prod: same SQL, run once by an operator; documented in `docs/operations/` when `[E0-8]` lands.

**Role names are fixed** (`hms_owner`, `hms_app`); V1 references them directly. If a deployment needs different names, introduce a Flyway placeholder then — not before.

**V1 grants** (run as `hms_owner`):
```sql
REVOKE ALL ON SCHEMA hms FROM PUBLIC;
GRANT USAGE ON SCHEMA hms TO hms_app;
REVOKE CREATE ON SCHEMA public FROM PUBLIC;         -- already the default on PG15+, explicit for clarity
DO $$ BEGIN EXECUTE format('REVOKE TEMPORARY ON DATABASE %I FROM PUBLIC', current_database()); END $$;

-- Default for every future table/sequence created by hms_owner in hms:
ALTER DEFAULT PRIVILEGES FOR ROLE hms_owner IN SCHEMA hms
  GRANT SELECT, INSERT, UPDATE ON TABLES TO hms_app;
ALTER DEFAULT PRIVILEGES FOR ROLE hms_owner IN SCHEMA hms
  GRANT USAGE, SELECT ON SEQUENCES TO hms_app;
ALTER DEFAULT PRIVILEGES FOR ROLE hms_owner IN SCHEMA hms
  GRANT EXECUTE ON FUNCTIONS TO hms_app;
```
- **`DELETE` is not a default grant.** No hard deletes is the rule; a table that genuinely needs `DELETE` (e.g. session rows, idempotency-key expiry) gets an explicit `GRANT DELETE` in its own migration with a comment why.
- **Append-only tables** (`audit_event`, `payment`, `refund`, `credit_note`, issued-document tables) additionally `REVOKE UPDATE ON <table> FROM hms_app` in their migration **and** attach the trigger from section 7 (defence in depth, invariant I8).
- `flyway_schema_history` is owned by `hms_owner` and is created before V1's default privileges exist, so `hms_app` has no access to it.
- `TRUNCATE`, `REFERENCES`, `TRIGGER` are never granted to `hms_app`.

**Application configuration change** (part of `[E0-6]`):
| Variable | Used by | Notes |
|---|---|---|
| `HMS_DB_USERNAME` / `HMS_DB_PASSWORD` | runtime datasource | becomes `hms_app` |
| `HMS_DB_MIGRATION_USERNAME` / `HMS_DB_MIGRATION_PASSWORD` | `spring.flyway.user` / `password` | `hms_owner` |
| `HMS_DB_ADMIN_USERNAME` / `HMS_DB_ADMIN_PASSWORD` | Compose Postgres superuser (`POSTGRES_USER`) only | dev convenience; never given to the app |

Flyway runs in-process at startup with the migration credentials (Spring Boot `spring.flyway.user`). Running migrations as a separate job is deferred until a deployment needs it.

## 4. Organization ownership and same-org references (Planned)
Referenced by domain-model invariant I11. Detail is written by `[E1-6]`; the intent fixed now so V1 does not contradict it:
- Every business table has `organization_id uuid NOT NULL`, FK to `hms.organization(id)` once that table exists.
- High-risk parent tables expose `UNIQUE (organization_id, id)`; children reference them with composite FKs `(organization_id, <parent>_id) REFERENCES parent (organization_id, id)` so a row can never point at another org's row.
- RLS (`FORCE ROW LEVEL SECURITY`, `SET LOCAL app.organization_id`) is **not** part of the baseline: it depends on ADR-0010 (Proposed) and the `[E1-2]` spike. V1 must only keep `hms_app` `NOBYPASSRLS` and non-owner so RLS *can* be enforced later.

## 5. Extensions
| Extension | Why | Needed by |
|---|---|---|
| `btree_gist` | `EXCLUDE USING gist (practitioner_id WITH =, tstzrange(...) WITH &&)` mixes a scalar equality with a range overlap (invariant I4) | appointment (M2) |
| `pg_trgm` | Fuzzy patient name search (PRD PAT-4) via trigram GIN index | patient (M2) |

Both are *trusted* extensions on PG13+, so `hms_owner` (database owner) can create them without superuser:
```sql
CREATE EXTENSION IF NOT EXISTS btree_gist WITH SCHEMA hms;
CREATE EXTENSION IF NOT EXISTS pg_trgm    WITH SCHEMA hms;
```
Installed in V1 (not when first used) so the privilege question is settled once and later migrations are plain DDL. `pgcrypto` / `uuid-ossp` are **not** installed: UUIDs come from the app (ADR-0004) and `gen_random_uuid()` is core since PG13 if ever needed.

## 6. Document numbering — `document_sequence`
One generic gapless counter table for business keys that must be sequential: invoice number (BR-B2, gapless per org per financial year), credit note number, receipt number, UHID (BR-P2, unique and never reused; gapless is harmless there).

```sql
CREATE TABLE hms.document_sequence (
    organization_id uuid        NOT NULL,   -- FK to organization added by its migration (section 4)
    document_type   text        NOT NULL,
    period_key      text        NOT NULL,   -- 'FY2026-27' per financial year; 'CY2026' per calendar year; 'ALL' never resets (UHID)
    next_value      bigint      NOT NULL DEFAULT 1,
    created_at      timestamptz NOT NULL,
    updated_at      timestamptz NOT NULL,
    CONSTRAINT pk_document_sequence PRIMARY KEY (organization_id, document_type, period_key),
    CONSTRAINT ck_document_sequence_type CHECK (document_type IN ('UHID','ADMISSION','INVOICE','CREDIT_NOTE','RECEIPT')),
    CONSTRAINT ck_document_sequence_next CHECK (next_value >= 1),
    CONSTRAINT ck_document_sequence_period CHECK (period_key = 'ALL' OR period_key ~ '^(FY[0-9]{4}-[0-9]{2}|CY[0-9]{4})$')
);
```
- New `document_type` values are added by a later migration that replaces the CHECK.
- **Allocation** (one statement, inside the caller's transaction):
  ```sql
  INSERT INTO hms.document_sequence (organization_id, document_type, period_key, next_value, created_at, updated_at)
  VALUES (:org, :type, :period, 2, :now, :now)
  ON CONFLICT (organization_id, document_type, period_key)
  DO UPDATE SET next_value = hms.document_sequence.next_value + 1, updated_at = EXCLUDED.updated_at
  RETURNING next_value - 1 AS allocated;
  ```
  The row lock taken by the upsert is held until the business transaction commits; a rollback rolls the counter back, so **numbers are gapless** and concurrent issuers in the same org/type/period serialise (accepted cost, ADR-0012). Different orgs/types/periods never block each other.
- **Lock order:** allocate the number **last**, after taking bed → admission → invoice locks (CLAUDE.md section 4), to keep the serialised section short and avoid deadlocks.
- **Ownership:** a single `DocumentNumberAllocator` in the `shared` kernel (infrastructure adapter, plain JDBC — not a JPA entity) is the only code touching this table. Modules call it through the shared kernel; they never query the table. This replaces the billing-owned `InvoiceNumberSequence` entity listed in `domain-model.md` section 2 (section 10, D3).
- **Formatting** is done by the owning module; the table stores only the integer. Examples from `docs/api/api-design.md`: invoice `2026-27/000031` (FY), receipt `RCT-2026-27/000044` (FY), admission `ADM-2026-0042` (CY), UHID `HMS-000124` (ALL).
- **Financial year:** April–March (BR-B2). `period_key` is derived from the issue instant converted to the **organization's time zone** (section 10, D2).
- **Privileges:** default `SELECT, INSERT, UPDATE` to `hms_app`; **no** `DELETE`.

## 7. Immutability function — `hms.reject_modification()`
Shared trigger function for append-only tables and immutable states (invariants I7, I8, I10).
```sql
CREATE FUNCTION hms.reject_modification() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    RAISE EXCEPTION 'immutable row: % on %.% is not allowed', TG_OP, TG_TABLE_SCHEMA, TG_TABLE_NAME
        USING ERRCODE = 'HM001';
END;
$$;
REVOKE ALL ON FUNCTION hms.reject_modification() FROM PUBLIC;
```
- **Append-only tables** attach it unconditionally:
  `CREATE TRIGGER trg_<table>_immutable BEFORE UPDATE OR DELETE ON hms.<table> FOR EACH ROW EXECUTE FUNCTION hms.reject_modification();`
  plus `BEFORE TRUNCATE ... FOR EACH STATEMENT` for the same function.
- **State-dependent immutability** (issued invoice and its items, finalized encounter children) uses a `WHEN (...)` clause on the trigger or a small table-specific function written by that module's migration; it raises the same `HM001`.
- No `SECURITY DEFINER`: the function needs no privileges, it only raises. Triggers fire for every role including `hms_owner`, so a manual `UPDATE` by an operator is also rejected — corrections go through credit notes/refunds/addenda.
- **Error mapping:** SQLSTATE `HM001` is translated in the shared web layer (`ProblemDetailsHandler`) to `409` with a module-specific `code` (e.g. `INVOICE_IMMUTABLE`, PRD BIL-4). Reaching the trigger means an application state check was missed, so it is also logged at `WARN` (no row values — table name and operation only).

## 8. Baseline migration (`V1__baseline.sql`) and order
V1 contains, in order: extensions (section 5) → schema privileges and default privileges (section 3) → `hms.reject_modification()` (section 7) → `hms.document_sequence` (section 6). It creates no business tables.

Planned order after V1 (each in its issue): `audit_event` + partitions `[E1-1]` → `organization`, FK on `document_sequence` `[E1-6]` → identity (users, roles, permissions, sessions) `[E1-3]`/`[E1-5]` → RLS policies `[E1-6]` (if ADR-0010 accepted) → M2+ modules.

## 9. Tests required for `[E0-6]`
Integration tests (Testcontainers `postgres:17-alpine` with the role init script from section 3):
1. Flyway migrates an empty database as `hms_owner`; the app starts and connects as `hms_app` (acceptance: "Migration runs on Testcontainers").
2. As `hms_app`: `CREATE TABLE hms.x(...)`, `CREATE TABLE public.x(...)`, `ALTER TABLE hms.document_sequence ...`, `DROP TABLE ...` and `CREATE TEMP TABLE` all fail with SQLSTATE `42501` (acceptance: "app role lacks DDL"). The same statements succeed as `hms_owner`, proving the negative test isn't failing for an unrelated reason.
3. `hms_app` attributes: not superuser, no `CREATEDB`/`CREATEROLE`/`BYPASSRLS`, owns no objects (`pg_class.relowner`).
4. `document_sequence`: sequential allocation 1, 2, 3; rollback does not consume a number; **two concurrent transactions** for the same key get distinct consecutive numbers with no gap; different org or period are independent; `DELETE` as `hms_app` fails with `42501`.
5. `reject_modification()`: on a test-only table with the trigger attached, `UPDATE`, `DELETE` and `TRUNCATE` fail with SQLSTATE `HM001` (as both roles).
6. Both extensions present in schema `hms`.

All test data synthetic (random UUIDs, no names).
