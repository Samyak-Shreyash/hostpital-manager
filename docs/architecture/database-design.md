## 2. Conventions (apply to every migration from V1)
- **Schema:** everything lives in `hms` (ADR-0003). Nothing is created in `public`. Objects are always schema-qualified in migrations.
- **Names:** `snake_case`; tables singular (`patient`, `invoice_item`); constraints `pk_<table>`, `fk_<table>_<ref>`, `uq_<table>_<cols>`, `ck_<table>_<rule>`, `ex_<table>_<rule>`; indexes `ix_<table>_<cols>`; triggers `trg_<table>_<purpose>`.
- **Standard columns** on business tables:
  | Column | Type | Notes |
  |---|---|---|
  | `id` | `uuid` PK | UUIDv7 generated by the app (ADR-0004); **no DB default** |
  | `organization_id` | `uuid NOT NULL` | FK to `organization` once it exists (section 4) |
  | `created_at`, `updated_at` | `timestamptz NOT NULL` | UTC; set by the app from the injected `Clock`, not `now()` defaults, so tests control time |
  | `version` | `bigint NOT NULL DEFAULT 0` | optimistic locking (`@Version`) on mutable aggregates only; immutable/append-only tables omit it |
- **Types:** money `NUMERIC(14,2)` (ADR-0012); instants `timestamptz`; dates `date`; enums as `text` + `CHECK (col IN (...))` (not PG enums — adding values to a PG enum cannot run inside a transaction and is awkward to reverse); free text `text` (no arbitrary `varchar(n)`; length limits live in Bean Validation, plus a `CHECK (char_length(...))` where a hard limit matters).
- **No hard deletes** of clinical or financial data: lifecycle `status` columns instead (CLAUDE.md section 5).
- **Flyway:** forward-only `V<n>__<description>.sql` in `backend/src/main/resources/db/migration` (ADR-0013). A merged migration is never edited; fixes are new migrations. No `undo` scripts. One migration = one logical change, runs in a single transaction (avoid `CREATE INDEX CONCURRENTLY` unless the migration is marked non-transactional and reviewed).

## 3. Roles and privileges (ADR-0015, Accepted)
Two roles with separate credentials. The application **never** connects with DDL rights.

| Role | Login | Purpose | Privileges |
|---|---|---|---|
| `hms_owner` | yes (used only by Flyway) | Owns the database, schema `hms` and all objects; runs migrations | Owner of all objects. Not superuser in staging/prod |
| `hms_app` | yes (runtime datasource) | Application runtime | `CONNECT` on db; `USAGE` on `hms`; DML per table as granted below. **No** `CREATE` on db or any schema, no `TEMP`, not owner of anything, `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS` |

**Who creates the roles.** Roles are cluster-level and need passwords, so they are **provisioned outside Flyway** (no secrets in migrations):
- Compose dev stack: an init script mounted into the Postgres container's `/docker-entrypoint-initdb.d/` creates `hms_owner` (owner of the `HMS_DB_NAME` database) and `hms_app` from env vars. Runs only on an empty volume — existing dev volumes must be recreated once (`docker compose ... down -v`).
- Testcontainers / CI: the same script via `withInitScript`/`withCopyFileToContainer`, so tests exercise the real grants.
- Staging/prod: same SQL, run once by an operator; documented in `docs/operations/` when `[E0-8]` lands.

**Role names are fixed** (`hms_owner`, `hms_app`); V1 references them directly. If a deployment needs different names, introduce a Flyway placeholder then — not before.

**V1 grants** (run as `hms_owner`):
```sql
REVOKE ALL ON SCHEMA hms FROM PUBLIC;
GRANT USAGE ON SCHEMA hms TO hms_app;
REVOKE CREATE ON SCHEMA public FROM PUBLIC;         -- already the default on PG15+, explicit for clarity
DO $$ BEGIN EXECUTE format('REVOKE TEMPORARY ON DATABASE %I FROM PUBLIC', current_database()); END $$;

-- Default for every future table/sequence created by hms_owner in hms:
ALTER DEFAULT PRIVILEGES FOR ROLE hms_owner IN SCHEMA hms
  GRANT SELECT, INSERT, UPDATE ON TABLES TO hms_app;
ALTER DEFAULT PRIVILEGES FOR ROLE hms_owner IN SCHEMA hms
  GRANT USAGE, SELECT ON SEQUENCES TO hms_app;
ALTER DEFAULT PRIVILEGES FOR ROLE hms_owner IN SCHEMA hms
  GRANT EXECUTE ON FUNCTIONS TO hms_app;
```
- **`DELETE` is not a default grant.** No hard deletes is the rule; a table that genuinely needs `DELETE` (e.g. session rows, idempotency-key expiry) gets an explicit `GRANT DELETE` in its own migration with a comment why.
- **Append-only tables** (`audit_event`, `payment`, `refund`, `credit_note`, issued-document tables) additionally `REVOKE UPDATE ON <table> FROM hms_app` in their migration **and** attach the trigger from section 7 (defence in depth, invariant I8).
- `flyway_schema_history` is owned by `hms_owner` and is created before V1's default privileges exist, so `hms_app` has no access to it.
- `TRUNCATE`, `REFERENCES`, `TRIGGER` are never granted to `hms_app`.

**Application configuration change** (part of `[E0-6]`):
| Variable | Used by | Notes |
|---|---|---|
| `HMS_DB_USERNAME` / `HMS_DB_PASSWORD` | runtime datasource | becomes `hms_app` |
| `HMS_DB_MIGRATION_USERNAME` / `HMS_DB_MIGRATION_PASSWORD` | `spring.flyway.user` / `password` | `hms_owner` |
| `HMS_DB_ADMIN_USERNAME` / `HMS_DB_ADMIN_PASSWORD` | Compose Postgres superuser (`POSTGRES_USER`) only | dev convenience; never given to the app |

Flyway runs in-process at startup with the migration credentials (Spring Boot `spring.flyway.user`). Running migrations as a separate job is deferred until a deployment needs it.

## 4. Organization ownership and same-org references
Referenced by domain-model invariant I11. Implemented by `[E1-6]` (V5, section 14):
- Every business table has `organization_id uuid NOT NULL`, FK to `hms.organization(id)`.
- High-risk parent tables expose `UNIQUE (organization_id, id)`; children reference them with composite FKs `(organization_id, <parent>_id) REFERENCES parent (organization_id, id)` so a row can never point at another org's row.
- RLS is **not** part of the baseline; `[E1-6]` introduced it (V5, section 14, including the tables excluded from it). The `[E1-2]` spike confirmed it works through HikariCP and JPA (ADR-0010, spike outcome). Pattern per business table: `ENABLE` + `FORCE ROW LEVEL SECURITY`; one policy `USING`/`WITH CHECK (organization_id = NULLIF(current_setting('app.organization_id', true), '')::uuid)`; the app sets the value per transaction with `set_config(..., true)`, never session-level. V1 keeps `hms_app` `NOBYPASSRLS` and non-owner so this can be enforced.

## 5. Extensions
| Extension | Why | Needed by |
|---|---|---|
| `btree_gist` | `EXCLUDE USING gist (practitioner_id WITH =, tstzrange(...) WITH &&)` mixes a scalar equality with a range overlap (invariant I4) | appointment (M2) |
| `pg_trgm` | Fuzzy patient name search (PRD PAT-4) via trigram GIN index | patient (M2) |

Both are *trusted* extensions on PG13+, so `hms_owner` (database owner) can create them without superuser:
```sql
CREATE EXTENSION IF NOT EXISTS btree_gist WITH SCHEMA hms;
CREATE EXTENSION IF NOT EXISTS pg_trgm    WITH SCHEMA hms;
```
Installed in V1 (not when first used) so the privilege question is settled once and later migrations are plain DDL. `pgcrypto` / `uuid-ossp` are **not** installed: UUIDs come from the app (ADR-0004) and `gen_random_uuid()` is core since PG13 if ever needed.

## 6. Document numbering — `document_sequence`
One generic gapless counter table for business keys that must be sequential: invoice number (BR-B2, gapless per org per financial year), credit note number, receipt number, UHID (BR-P2, unique and never reused; gapless is harmless there).

```sql
CREATE TABLE hms.document_sequence (
    organization_id uuid        NOT NULL,   -- FK to organization added by its migration (section 4)
    document_type   text        NOT NULL,
    period_key      text        NOT NULL,   -- 'FY2026-27' per financial year; 'CY2026' per calendar year; 'ALL' never resets (UHID)
    next_value      bigint      NOT NULL DEFAULT 1,
    created_at      timestamptz NOT NULL,
    updated_at      timestamptz NOT NULL,
    CONSTRAINT pk_document_sequence PRIMARY KEY (organization_id, document_type, period_key),
    CONSTRAINT ck_document_sequence_type CHECK (document_type IN ('UHID','ADMISSION','INVOICE','CREDIT_NOTE','RECEIPT')),
    CONSTRAINT ck_document_sequence_next CHECK (next_value >= 1),
    CONSTRAINT ck_document_sequence_period CHECK (period_key = 'ALL' OR period_key ~ '^(FY[0-9]{4}-[0-9]{2}|CY[0-9]{4})$')
);
```
- New `document_type` values are added by a later migration that replaces the CHECK.
- **Allocation** (one statement, inside the caller's transaction):
  ```sql
  INSERT INTO hms.document_sequence (organization_id, document_type, period_key, next_value, created_at, updated_at)
  VALUES (:org, :type, :period, 2, :now, :now)
  ON CONFLICT (organization_id, document_type, period_key)
  DO UPDATE SET next_value = hms.document_sequence.next_value + 1, updated_at = EXCLUDED.updated_at
  RETURNING next_value - 1 AS allocated;
  ```
  The row lock taken by the upsert is held until the business transaction commits; a rollback rolls the counter back, so **numbers are gapless** and concurrent issuers in the same org/type/period serialise (accepted cost, ADR-0012). Different orgs/types/periods never block each other.
- **Lock order:** allocate the number **last**, after taking bed → admission → invoice locks (CLAUDE.md section 4), to keep the serialised section short and avoid deadlocks.
- **Ownership:** a single `DocumentNumberAllocator` in the `shared` kernel (infrastructure adapter, plain JDBC — not a JPA entity) is the only code touching this table. Modules call it through the shared kernel; they never query the table. This replaces the billing-owned `InvoiceNumberSequence` entity listed in `domain-model.md` section 2 (section 10, D3).
- **Formatting** is done by the owning module; the table stores only the integer. Examples from `docs/api/api-design.md`: invoice `2026-27/000031` (FY), receipt `RCT-2026-27/000044` (FY), admission `ADM-2026-0042` (CY), UHID `HMS-000124` (ALL).
- **Financial year:** April–March (BR-B2). `period_key` is derived from the issue instant converted to the **organization's time zone** (section 10, D2).
- **Privileges:** default `SELECT, INSERT, UPDATE` to `hms_app`; **no** `DELETE`.

## 7. Immutability function — `hms.reject_modification()`
Shared trigger function for append-only tables and immutable states (invariants I7, I8, I10).
```sql
CREATE FUNCTION hms.reject_modification() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    RAISE EXCEPTION 'immutable row: % on %.% is not allowed', TG_OP, TG_TABLE_SCHEMA, TG_TABLE_NAME
        USING ERRCODE = 'HM001';
END;
$$;
REVOKE ALL ON FUNCTION hms.reject_modification() FROM PUBLIC;
```
- **Append-only tables** attach it unconditionally:
  `CREATE TRIGGER trg_<table>_immutable BEFORE UPDATE OR DELETE ON hms.<table> FOR EACH ROW EXECUTE FUNCTION hms.reject_modification();`
  plus `BEFORE TRUNCATE ... FOR EACH STATEMENT` for the same function.
- **State-dependent immutability** (issued invoice and its items, finalized encounter children) uses a `WHEN (...)` clause on the trigger or a small table-specific function written by that module's migration; it raises the same `HM001`.
- No `SECURITY DEFINER`: the function needs no privileges, it only raises. Triggers fire for every role including `hms_owner`, so a manual `UPDATE` by an operator is also rejected — corrections go through credit notes/refunds/addenda.
- **Error mapping:** SQLSTATE `HM001` is translated in the shared web layer (`ProblemDetailsHandler`) to `409` with a module-specific `code` (e.g. `INVOICE_IMMUTABLE`, PRD BIL-4). Reaching the trigger means an application state check was missed, so it is also logged at `WARN` (no row values — table name and operation only).

## 9. Tests required for `[E0-6]`
Integration tests (Testcontainers `postgres:17-alpine` with the role init script from section 3):
1. Flyway migrates an empty database as `hms_owner`; the app starts and connects as `hms_app` (acceptance: "Migration runs on Testcontainers").
2. As `hms_app`: `CREATE TABLE hms.x(...)`, `CREATE TABLE public.x(...)`, `ALTER TABLE hms.document_sequence ...`, `DROP TABLE ...` and `CREATE TEMP TABLE` all fail with SQLSTATE `42501` (acceptance: "app role lacks DDL"). The same statements succeed as `hms_owner`, proving the negative test isn't failing for an unrelated reason.
3. `hms_app` attributes: not superuser, no `CREATEDB`/`CREATEROLE`/`BYPASSRLS`, owns no objects (`pg_class.relowner`).
4. `document_sequence`: sequential allocation 1, 2, 3; rollback does not consume a number; **two concurrent transactions** for the same key get distinct consecutive numbers with no gap; different org or period are independent; `DELETE` as `hms_app` fails with `42501`.
5. `reject_modification()`: on a test-only table with the trigger attached, `UPDATE`, `DELETE` and `TRUNCATE` fail with SQLSTATE `HM001` (as both roles).
6. Both extensions present in schema `hms`.

All test data synthetic (random UUIDs, no names).

## 11. Audit events — `audit_event` (`V2__audit_event.sql`, `[E1-1]`)
ADR-0007, PRD AUD-1/2/4, invariant I8. Written only through `audit.api.AuditRecorder`.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | UUIDv7; PK is `(id, occurred_at)` because the table is partitioned by `occurred_at` |
| `organization_id` | `uuid NOT NULL` | FK to `organization` added by `[E1-6]` |
| `occurred_at` | `timestamptz NOT NULL` | from the injected `Clock` |
| `actor_id` | `uuid` | `NULL` = system or unauthenticated caller; FK to `app_user` added by `[E1-3]` |
| `action` / `entity_type` | `text` | `UPPER_SNAKE_CASE`, CHECKed |
| `entity_id` | `uuid` | nullable (e.g. failed login) |
| `outcome` | `text` | `SUCCESS` / `FAILURE` / `DENIED` |
| `correlation_id` | `text` | MDC `correlationId`, same shape the filter accepts |
| `changed_fields` | `text[]` | **field names only** (AUD-4); CHECK allows ≤ 50 camelCase/dotted names, so a phone number, e-mail or sentence is rejected |

- **No free-form metadata column** (no `jsonb`): there is nowhere to put a value, password, token or clinical text. New metadata needs a migration and review.
- **Append-only:** `REVOKE UPDATE` from `hms_app` (it never had `DELETE`/`TRUNCATE`), row trigger `BEFORE UPDATE OR DELETE` and statement trigger `BEFORE TRUNCATE` with `hms.reject_modification()` on the parent; each partition gets its own `TRUNCATE` trigger (not inherited). `hms_app` has no privileges on partitions directly — access only through the parent.
- **Same transaction:** `AuditRecorder.record` is `@Transactional(propagation = MANDATORY)`: it joins the caller's transaction and throws outside one. A failing audit insert rolls back the business change. Read-audit in a separate short transaction (ADR-0007) arrives with `[E3-7]`.
- **Partitions:** monthly `RANGE (occurred_at)` in UTC, named `audit_event_YYYY_MM`. `hms.ensure_audit_event_partitions(months_ahead 0..12)` creates the current month plus `months_ahead`; it is `SECURITY DEFINER` (owned by `hms_owner`, `search_path` pinned, argument bounded, advisory-locked) so `hms_app` can run it without DDL rights. V2 calls it with 3; `AuditPartitionMaintenance` calls it at startup and daily at 02:15 UTC (`hms.audit.partition-months-ahead`, `hms.audit.partition-cron`). **No default partition**: if maintenance stops, audit inserts fail once the horizon is reached — fail-closed by design.
- **Retention / dropping old partitions:** not implemented; retention period needs legal review (PRD section 7) before any partition is detached.
- Indexes: `(organization_id, occurred_at)`, `(organization_id, entity_type, entity_id, occurred_at)`, `(organization_id, actor_id, occurred_at)` for the viewer `[E1-9]`.

## 12. Users and sessions (`V3__identity_authentication.sql`, `[E1-3]`)
`hms.app_user` (table name avoids the reserved word `user`):

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | UUIDv7 |
| `organization_id` | `uuid NOT NULL` | FK to `organization` added by `[E1-6]`; `UNIQUE (organization_id, id)` for same-org FKs (section 4) |
| `email` | `text NOT NULL` | stored lower-case (`CHECK`); **unique across all orgs** (`uq_app_user_email`) because login is email-only |
| `full_name` | `text NOT NULL` | 1–200 chars |
| `password_hash` | `text NOT NULL` | BCrypt cost 12 (ADR-0005); never logged or audited |
| `status` | `text` | `ACTIVE` / `INACTIVE` (no hard delete) |
| `must_change_password` | `boolean` | default `true`; enforced by `[E1-4]` |
| `failed_login_count`, `locked_until` | `integer`, `timestamptz` | lockout: 5 failures → locked 15 min |
| `version`, `created_at`, `updated_at` | | optimistic locking, timestamps from the injected `Clock` |

- Login reads the row `FOR UPDATE`, so concurrent failed attempts cannot lose an increment.
- `audit_event.actor_id` now has an FK to `app_user (id)`.
- Spring Session JDBC tables `hms.spring_session` and `hms.spring_session_attributes` follow Spring Session's PostgreSQL schema; `spring.session.jdbc.initialize-schema=never`. `hms_app` gets `DELETE` on both (sessions are transient technical rows, not business data). `principal_name` holds the user id, so all of a user's sessions can be revoked (`[E1-7]`).
- Auth audit actions (entity `APP_USER`): `LOGIN_SUCCEEDED` (actor = user), `LOGIN_FAILED` (actor `NULL`; outcome `FAILURE`, or `DENIED` when locked/inactive), `ACCOUNT_LOCKED`, `LOGOUT`. A failed login for an unknown email is **not** audited: there is no organization to attribute it to.

## 13. Roles and permissions (`V4__identity_rbac.sql`, `[E1-5]`, ADR-0006)
| Table | Columns | Notes |
|---|---|---|
| `permission` | `code text` PK | Global catalogue, **not** org-owned; mirrors `com.hms.identity.api.Permissions` (an integration test compares both). `hms_app` has `SELECT` only: codes change by migration. |
| `role` | `id`, `organization_id`, `code`, `name`, `version`, `created_at`, `updated_at` | Org-owned data. `UNIQUE (organization_id, code)`; `UNIQUE (organization_id, id)` as target for same-org FKs; `code` upper snake case. |
| `role_permission` | `organization_id`, `role_id`, `permission_code` | PK `(role_id, permission_code)`; composite FK `(organization_id, role_id) → role`; FK to `permission`. |
| `user_role` | `organization_id`, `user_id`, `role_id` | PK `(user_id, role_id)`; composite FKs to `app_user (organization_id, id)` and `role (organization_id, id)`, so a user can only hold roles of their own organization. |

- Login loads the user's role codes and the union of their permissions into the session principal; the permissions become the Spring authorities. A change to a role takes effect on the user's next login (sessions are revoked on role change by role/user management).
- Default roles (PRD section 3 personas: `SYSTEM_ADMIN`, `FACILITY_ADMIN`, `DOCTOR`, `NURSE`, `RECEPTIONIST`, `ACCOUNTANT`) are code templates (`DefaultRoleTemplates`) copied into an organization by `RoleProvisioning.provisionDefaultRoles`, not seeded by the migration (no organization exists at migration time). The PRD's `report:read` maps to `report:clinical`.
- `DELETE` on `role_permission` / `user_role` is granted by `V6` (section 15). FK to `organization` and RLS policies were added by `[E1-6]` (section 14).

## 14. Organization and row-level security (`V5__organization_rls.sql`, `[E1-6]`, ADR-0010)
| Table | Columns | Notes |
|---|---|---|
| `organization` | `id`, `name`, `status` (`ACTIVE`/`INACTIVE`), `version`, `created_at`, `updated_at` | Minimal for M1; settings such as time zone come with organization management. No DELETE grant. |

- FKs to `organization(id)` from `document_sequence`, `app_user`, `role`, `role_permission`, `user_role` and `audit_event`. V5 backfills an `organization` row for any `organization_id` already present (dev databases) before adding them.
- **RLS tables** (`ENABLE` + `FORCE`, policy `org_isolation` with `USING` and `WITH CHECK` on `organization_id = NULLIF(current_setting('app.organization_id', true), '')::uuid`): `document_sequence`, `role`, `role_permission`, `user_role`. Every later org-owned table gets the same policy in the migration that creates it; `OrganizationIsolationIT` fails if a table with an `organization_id` column is neither under forced RLS nor listed below.
- **Excluded from RLS (ruling, 2026-11-12):** `organization` (it is the tenant itself), `app_user` (login looks the user up by email before any organization is known), `audit_event` (written by unauthenticated login flows; read only through the org-scoped audit viewer) and `spring_session` / `spring_session_attributes` (technical rows, no `organization_id`). `permission` is global reference data. App-level scoping by the principal's organization still applies to every query on these tables.
- **Context:** `OrganizationContext` (`com.hms.shared.tenancy`) yields the principal's organization (via `OrganizationPrincipal`, implemented by `AuthenticatedPrincipal`); `OrganizationTransactionListener` runs `set_config('app.organization_id', <org>, true)` as the first statement of every new transaction that has one. System or unauthenticated flows use `OrganizationContext.runAs(org, work)` or, when the organization is only learnt mid-transaction, `bindToCurrentTransaction(org)` (login after the email lookup; `RoleProvisioning.provisionDefaultRoles`). Both refuse an organization other than an authenticated principal's. No context means RLS tables return no rows (fail-closed).
- **Jobs:** audit partition maintenance runs without a principal; it touches only `audit_event` through a `SECURITY DEFINER` function, so it needs no context. Future jobs that touch RLS tables iterate organizations with `runAs`.
- **Migrations:** `FORCE` binds `hms_owner` too, so a migration that seeds or backfills rows of an RLS table must `set_config('app.organization_id', <org>, true)` per organization first.

## 15. User and role management (`V6__user_role_management.sql`, `[E1-7]`)
- **Explicit `DELETE` grants** to `hms_app` on `user_role` (remove a role from a user) and `role_permission` (remove a permission from a role). Justification: pure mapping rows with no identity and no clinical or financial data; each change is audited (`USER_UPDATED` / `ROLE_UPDATED`, field names) in the same transaction. No other table gains `DELETE`; `role` and `app_user` rows are never deleted.
- **No `status` column on `role`** (decision for `[E1-7]`): api-design.md section 3 has no role deactivation, and an unused role is harmless. A role can be emptied of permissions instead. Add a status with its own migration if a requirement appears.
- `app_user` is outside RLS (section 14), so every user-management query filters by the caller's `organization_id` explicitly (`AppUserRepository.findByIdAndOrganization*`, `UserAdminRepository`); the role tables are under RLS and queried in the principal's organization context.
- **Last administrator rule**: changes that can remove an administrator (deactivate, role replacement, role permission edit) first `SELECT ... FOR UPDATE` the `organization` row, then count active users holding both `user:update` and `role:manage` before and after, and roll back with `409 LAST_ADMINISTRATOR` if the count would drop from at least one to zero. Lock order: organization, then user/role rows.
- **Session revocation**: `DELETE FROM hms.spring_session WHERE principal_name = <user id>` (attributes cascade), optionally excluding the caller's own `session_id`. Applied on deactivate, admin password reset, role change, role permission change (for each holder) and self-service password change.

## 16. Organization settings and bootstrap (`V7__organization_settings.sql`, `[E2-1]`)
- `organization` gains `timezone text NOT NULL DEFAULT 'Asia/Kolkata'` (IANA id; the application validates it against the JDK zone list, the CHECK bounds its shape), `gstin text NULL` (CHECK `^[0-9]{2}[A-Z]{5}[0-9]{4}[A-Z][1-9A-Z]Z[0-9A-Z]$`, format only) and `address text NULL` (1-500 chars). No new grants: still no DELETE on `organization`; the existing `name` CHECK (1-200) applies.
- Settings updates are compare-and-set on `version` (`UPDATE ... WHERE id = ? AND version = ?`). `organization` is outside RLS, so each query is scoped by the principal's organization explicitly.
- Bootstrap (organization, default roles, first System Administrator) runs in one transaction under `pg_advisory_xact_lock(hashtext('hms.bootstrap'))`, so concurrent instances cannot create two organizations; the loser finds one and does nothing. Lock order unaffected (nothing else is locked first).

## 17. Departments and specialties (`V8__department_specialty.sql`, `[E2-2]`)
- `department` and `specialty` (organization module) share one shape: `id uuid PK`, `organization_id` (FK `organization`), `code text` (CHECK `^[A-Z0-9_]{2,20}$`), `name text` (1-100), `active boolean NOT NULL DEFAULT true`, `version bigint`, `created_at`, `updated_at`.
- `UNIQUE (organization_id, code)` enforces the per-organization code rule (the same code may exist in another organization); the insert is `ON CONFLICT DO NOTHING`, so concurrent duplicates lose cleanly and surface as `409 DUPLICATE_DEPARTMENT_CODE` / `DUPLICATE_SPECIALTY_CODE`. `UNIQUE (organization_id, id)` is the target for same-org composite FKs from later tables (practitioner, ward).
- Both tables are under `ENABLE` + `FORCE ROW LEVEL SECURITY` with the standard `org_isolation` policy (section 14). Queries also filter by the principal's organization.
- No DELETE grant: `hms_app` has the default SELECT/INSERT/UPDATE only. Retiring an entry is `active = false` (a test asserts the database refuses DELETE). The code is immutable after creation. Updates are compare-and-set on `version`.

## 18. Service catalog and prices (`V9__service_catalog.sql`, `[E2-3]`)
- `service_catalog_item` (billing module): `id`, `organization_id` (FK), `code` (`^[A-Z0-9_]{2,30}$`, `UNIQUE (organization_id, code)`), `name` (1-150), `active`, `version`, timestamps; `UNIQUE (organization_id, id)` is the target of same-org composite FKs (invoice items later). No DELETE grant; retire with `active = false`.
- `service_price`: one row per price version: `amount numeric(14,2) CHECK (amount >= 0)`, `effective_from timestamptz NOT NULL`, `effective_to timestamptz NULL` (NULL = open-ended), `created_by`, `created_at`; composite FK `(organization_id, service_id)` to the item.
- **Range choice**: `timestamptz` pair, not `daterange`, because a price can change mid-day and invoices are priced at an instant. Semantics are half-open `[effective_from, effective_to)`: the end instant belongs to the successor. `EXCLUDE USING gist (service_id WITH =, tstzrange(effective_from, effective_to, '[)') WITH &&)` (needs `btree_gist`, V1) makes overlap impossible even under concurrent inserts; `CHECK (effective_to IS NULL OR effective_to > effective_from)`. Adjacent ranges are allowed. "Price at T" is `effective_from <= T AND (effective_to IS NULL OR T < effective_to)`. Instants are stored and compared at microsecond precision (the service truncates).
- **Immutability**: `hms_app` has no DELETE and only column-level `UPDATE (effective_to)`; trigger `hms.guard_service_price()` additionally rejects deleting a row or changing anything except setting `effective_to` once from NULL. A price change = close the latest open version at the new start, insert the new open-ended one, both under a `SELECT ... FOR UPDATE` on the service row (lock order: service, then prices).
- Both tables are under `ENABLE` + `FORCE ROW LEVEL SECURITY` with the standard `org_isolation` policy (section 14). Invoices copy the amount (and may keep the price id); they never reference a price for its value.

## 19. Patients (`V10__patient.sql`, `[E3-1]`)
- `patient`: `id`, `organization_id` (FK), `uhid text` (`HMS-` + at least 6 digits), `full_name` (2-120), `sex` (M/F/O/U), `date_of_birth date NOT NULL` (an estimated age is stored as a derived date with `dob_estimated = true`), `phone` (E.164), `status` (`ACTIVE/INACTIVE/MERGED/DECEASED`, BR-P4), `created_by`, `version`, timestamps. `UNIQUE (organization_id, uhid)` (BR-P2), `UNIQUE (organization_id, id)` as the same-org FK target.
- `patient_address` (one current address per type via partial unique index `(patient_id, address_type) WHERE is_current`) and `patient_contact` (`contact_type = 'EMERGENCY'`): composite FK `(organization_id, patient_id)` to `patient (organization_id, id)`.
- UHID numbers come from `document_sequence` (`document_type = 'UHID'`, `period_key = 'ALL'`) through `com.hms.shared.numbering.DocumentNumberAllocator` (section 6): the registration allocates after validation and just before the inserts, the counter row lock is held until commit, a rollback returns the number, so the sequence is gapless per organization and registrations of one organization serialise on that row. The counter row is created by the first allocation (`INSERT ... ON CONFLICT DO UPDATE`, under the organization's RLS context).
- All three tables: `ENABLE` + `FORCE ROW LEVEL SECURITY` with the standard `org_isolation` policy (section 14). No DELETE grant. Search indexes (trigram name) and duplicate detection arrive with `[E3-2]` / `[E3-3]`.
